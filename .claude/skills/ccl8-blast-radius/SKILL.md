# ccl8 영향 분석

"안전할 것이다"는 근거가 아니다. 변경의 안전 주장 하나를 골라 실제로 실행해서 증명한다.

## 절차

1. **안전 주장을 쓴다.** "이 변경 뒤에도 ...은 그대로다"를 한 문장으로 쓴다. 예: "기존 저장 파일이 오류 없이 열리고 아이템 수량이 같다", "Dedicated 서버에서 클라이언트의 장비가 그대로 복제된다".
2. **영향 범위를 찾는다.**
   - 바뀐 심볼마다 `graft callers <symbol> --depth all`.
   - 리플렉션 이름, `Config/*.ini`, 에셋이 참조하는 클래스·프로퍼티 이름. 에셋 참조는 이름 검색만으로 다 찾지 못하므로 리다이렉트가 필요한지 확인한다.
   - 저장 형식의 버전과 이전 저장의 읽기 경로.
   - 복제 프로퍼티, RPC, 네트워크 모드별 분기.
   - 공용 모듈(`Source/KSI*/`)이면 독립성 검사 `Tools/Validation/run_framework_isolation.ps1`.
3. **가장 비싼 실패를 고른다.** 찾은 범위 가운데 실패하면 가장 되돌리기 어려운 것(사용자 저장 손상, 네트워크 비동기, 에셋 참조 끊김)을 고르고, 1단계의 주장을 그 실패에 맞게 고친다.
4. **실행으로 증명한다.** 주장을 판정하는 실행을 고른다. 이전 커밋에서 만든 저장을 새 빌드로 열기, 해당 네트워크 모드의 스모크, 자동화 테스트. 실행 방법과 증거 기록은 `ccl8-verify` 스킬을 따른다. 변경 전 빌드에서 같은 실행이 통과하는 것도 확인해 실행 자체가 유효한지 본다.
5. **보고한다.** 안전 주장, 실행 명령, 결과와 증거 경로, 증명하지 않은 영향 범위를 적는다. 증명하지 않은 범위는 위험도와 함께 남긴다.
