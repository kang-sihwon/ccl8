# ccl8 코드 리뷰

리뷰는 지적까지다. 사용자가 수정을 요청하지 않으면 코드를 고치지 않는다. 기준 문서는 `../../../Docs/Coding.md`(규칙)와 변경 영역의 사양서(`../../../Docs/README.md`에서 찾는다)다.

## 절차

1. **범위를 정한다.** 리뷰할 diff를 고정한다(`git diff <base>...<head>`, 커밋 범위, 작업 트리). 변경의 목적은 커밋 메시지, 작업 지도, 사용자 설명에서 한 줄로 적는다.
2. **기계 검사를 돌린다.** `node Tools/Agent/cpp-rules.cjs check <바뀐 파일>`, `node Tools/Agent/cpp-rules.cjs format --base <base>`, `node Tools/Agent/floor-guard.cjs --base <base>`. 결과는 지적으로 옮기되 사람이 다시 판단하지 않는다.
3. **규칙 축을 본다.** Coding에서 검사기가 보지 않는 것: 헤더 영역 순서와 선언 묶음, CPP 정의 순서, 함수 본문의 단계 구분, `uint8` 불리언 외의 코드 관례, UE5 현행 시스템 우선(결정 10), 형식 정리와 동작 변경의 분리.
4. **사양 축을 본다.** 변경이 사양서의 계약과 결정을 지키는가. 소유자·수명·서버 권위·복제 범위·저장 경계(Coding의 "장르에 독립적인 베이스 시스템 설계"), 실패·종료·재사용 경로, 네트워크 모드별 동작, 저장 형식의 호환. 바뀐 심볼은 `graft callers <symbol> --depth all`로 호출자를 모두 확인한다.
5. **검증을 본다.** 완료 보고에 프로젝트 파일 생성, 빌드, 검사, 실행 검증 결과가 각각 있는가. 게임 동작을 바꿨는데 증거 강도가 변경 경로보다 약하면 지적한다.
6. **보고한다.** 아래 형식으로 낸다.

## 지적 형식

첫 줄에 판정을 쓴다: `머지 가능`, `수정 뒤 머지`, `다시 설계`. 그다음 심각한 것부터 지적을 적는다. 지적이 없으면 "지적 없음"이라고 쓴다.

지적마다 다음을 한 묶음으로 쓴다.

- 접두어: `[결함]`(잘못 동작한다), `[설계 위험]`(지금은 동작하지만 계약·수명·확장에서 깨질 수 있다), `[개선]`(선택 사항).
- 위치(`path:line`), 원인, 영향, 확인 방법 또는 재현 조건.
- 판정 분류: `조치`(고쳐야 한다), `검토`(사용자 판단이 필요하다), `참고`(알아 두면 된다).

다른 리뷰어나 도구의 지적을 받아 정리할 때는 각 지적에 `조치`, `검토`, `참고`, `기각` 중 하나를 붙이고, `기각`에는 근거가 되는 코드나 문서 위치를 적는다.

성능 주장에는 빌드·장면·설정 조건과 실측값이 있어야 한다. 실측이 없으면 `[설계 위험]`이나 `검토`로 적고 측정 방법을 붙인다. 확인하지 못한 동작은 미확인으로 남긴다.
