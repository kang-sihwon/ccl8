# ccl8 진단

진단은 **루프**에서 시작한다. 루프는 버그가 있으면 실패(red)하고 고쳐지면 통과(green)하는, 짧고 같은 결과를 내는 실행이다. 루프 없이 코드를 읽어 원인을 단정하지 않는다.

## 절차

1. **증상을 적는다.** 기대 동작, 실제 동작, 처음 본 조건(맵, 네트워크 모드, 빌드 구성, 커밋)을 한 줄씩 적는다. 로그가 있으면 첫 `FAIL`, `Assertion failed:`, `Fatal error:`, `Ensure condition failed:` 줄을 인용한다.
2. **루프를 만든다.** 아래 후보 중 가장 짧은 것을 고른다. 루프가 red인 것을 한 번 확인해야 이 단계가 끝난다. red를 만들 수 없으면 재현 조건을 하나씩 바꿔 보고, 그래도 안 되면 재현 불가로 보고하고 사용자에게 조건을 묻는다.

   | 후보 | 쓸 때 |
   |---|---|
   | 자동화 테스트(`Tools/Validation/run_automation.ps1 -Filter <경로>`) | 계산·데이터·계약처럼 맵 없이 확인되는 동작 |
   | 기능 스모크(`Tools/Validation/run_*.ps1`) | 맵·네트워크·저장이 필요한 동작. 색인은 `ccl8-verify` 스킬의 `features/README.md` |
   | MCP PIE | 실제 키·마우스·포커스가 필요한 동작. 절차는 `ccl8-verify` 스킬의 `references/mcp-pie.md` |
   | 저장 세계 재생 | 특정 저장 파일에서만 나는 문제. 원본 저장은 복사본으로 실행한다 |
   | 빌드 | 컴파일·링크·UHT 오류. `Docs/Coding.md`의 완료 검증 1-2단계 |

3. **좁힌다.** 가설을 하나 세우고, 그 가설이 맞을 때와 틀릴 때 결과가 갈리는 관측 하나를 정한 뒤 실행한다. 관측 수단은 로그 줄 추가, 조건 하나 바꾸기, 커밋 이분 탐색(`git bisect`는 사용자 확인 뒤), 입력 경로 바꾸기다. 가설마다 결과를 한 줄로 남긴다. 프로젝트 호출 관계는 `graft callers`, 엔진 동작은 `graft_ue58`와 엔진 소스의 `path:line`으로 확인한다.
4. **원인을 말한다.** 원인은 "이 조건에서 이 코드가 이 값을 만들어 이 결과가 난다"로 적고 근거 위치를 붙인다. 증상과 원인 사이에 확인하지 못한 고리가 있으면 그 고리를 미확인으로 적는다.
5. **고치고 루프를 돌린다.** 루프가 green이 돼야 끝난다. 같은 계열의 다른 경로(다른 네트워크 모드, 다른 맵)가 있으면 그 루프도 돌린다. 저렴한 자동화 테스트가 루프였다면 그 테스트를 저장소에 남긴다.
6. **재발을 막는다.** 같은 실수가 다시 날 수 있으면 구조, 타입·검사, 시험, 문서 순으로 막을 수단을 고른다. 반복된 실수라면 사용자에게 `/ccl8-retro`를 제안한다.

## 경계

- 이번 진단이 시작한 에디터·게임 프로세스만 종료한다. 사용자가 연 에디터는 건드리지 않는다.
- 원인을 찾으려고 시간 제한을 늘리거나 검사를 끄지 않는다. `Tools/Agent/floor-guard.cjs`가 그런 변경을 찾는다.
- 수정이 게임 동작을 바꾸면 끝에 `ccl8-verify`로 실행 검증을 한다.
