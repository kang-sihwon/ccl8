# 설계 결정 이력

추가·번복 절차는 [WritingGuide](WritingGuide.md)를 따른다.

## 2026-10-05 — 결정 1: 제작 방향과 단기 콘텐츠 범위

### 배경

사용자는 CCL 신청 계획서에 소울라이크 RPG 제작을 이미 기재했다고 설명했다. 전체 작업 방향과 그래픽 스타일은 Orbis와 같게 유지하되 장기 프로젝트가 아닌 3-4개월 내 완성을 지시했다.

### 결정

소울라이크 RPG를 유지하고 마을 하나, 보스 하나, 보스에게 가는 동안 싸울 서로 다른 일반 몹 몇 종류, NPC 몇 명과 간단한 시나리오를 만든다. 그래픽 스타일은 Orbis를 기준으로 한다. 정확한 일반 몹·NPC 수와 세부 전투 규칙은 아직 결정하지 않았다.

범위 정본은 [Direction](Direction.md)이다. CCL 프로그램 기간 3개월과 제작 목표 3-4개월은 구분하며 실제 제출일은 미확인으로 남긴다.

### 트레이드오프

제한된 공간과 보스에 제작 시간을 집중할 수 있는 대신 세계의 규모와 콘텐츠 다양성은 작아진다. Orbis의 전체 장기 시스템을 먼저 구현하는 대안은 이번 기한과 충돌할 수 있으므로 개별 필요성을 검토한다.

## 2026-10-05 — 결정 2: AI 주도 제작과 사용자 검토

### 배경

초기 구성은 사용자가 게임 코드를 작성하고 AI가 설계·예시·리뷰를 제공하는 방식이었다. 사용자는 ccl8에서는 AI가 주도해서 작업하고 자신은 검토, 수정 사항과 방향 지시를 맡는다고 명시했다.

### 결정

AI가 합의된 제작 범위의 기획, 아트 제안, 게임 코드·설정·에셋 제작, 통합, 검증과 문서화를 주도한다. 사용자는 결과를 검토하고 방향과 수정 사항을 지시한다. 이 역할 분담은 초기 Guide·Coding·설계 스킬의 사용자 직접 구현 기본값을 대체한다.

AI는 합의된 범위 안의 통상적인 구현을 위해 매 파일마다 재승인을 요구하지 않는다. 검토 가능한 작업 단위로 결과, 검증과 미확인 사항을 제시한다. 방향과 범위 변경은 사용자 검토 대상으로 남긴다. 힌트 훈련은 요청할 때 적용한다.

이번 작업은 제작 방향과 지침의 문서화이며 UE 프로젝트나 게임 구현을 완료했다는 뜻은 아니다.

### 트레이드오프

사용자의 직접 구현 시간을 줄이고 AI가 작업을 이어갈 수 있다. 반면 사용자가 코드를 작성하며 얻는 학습과 세부 통제는 줄어들 수 있다. 작은 결과물 단위의 검토와 실제 실행 검증으로 진행 상황을 확인한다.

## 2026-10-05 — 결정 3: 멀티플레이 구현과 제작 순서

### 배경

사용자는 초기 코드 베이스 논의에서 이번 CCL에 멀티플레이를 구현한다고 명시했다. 전투, 성장 기능과 콘텐츠를 순차로 만드는 계획을 검토한 뒤, 처음에는 에디터에서 플레이하므로 시작 화면을 후반으로 미루자고 제안했다. 사용자는 이를 반영한 작업 순서의 문서 저장을 요청했다.

### 결정

멀티플레이 기본 흐름, 일반 몹 한 종류와 최소 전투, 보스 초안과 승리·종료 조건 순으로 게임을 연결한다. 이후 인벤토리·장비·능력치·스킬의 기능과 UI를 구현하고, 일반 몹·보스·NPC·상점·퀘스트·튜토리얼을 보강한다. 시작 화면·방 생성·접속 UI·세이브·로드·설정을 만든 뒤 최종 패키징과 전체 흐름 검증을 진행한다.

초기는 PIE로 테스트 맵에 직접 진입하고 서버·클라이언트 실행 설정으로 멀티플레이를 검증한다. 별도 프로세스 접속과 패키징 실행 확인도 초기 기본 흐름부터 보스 초안까지의 작업 중에 수행한다. 작업 순서와 완료 기준의 정본은 [StudyRoadmap](StudyRoadmap.md)이다.

멀티플레이 인원과 서버 형태 등 세부 요구는 [GameDesign](GameDesign.md)에 미정으로 남긴다. 월별 배분은 일정 초안이며 이번 결정은 구현 완료나 납기 확정을 뜻하지 않는다.

### 트레이드오프

시작 화면부터 만드는 대안보다 멀티플레이와 전투 흐름을 먼저 확인할 수 있다. 대신 실제 시작·접속 UI를 포함한 사용자 경험의 검증은 후반에 이뤄진다. 초기 별도 프로세스·패키징 확인으로 에디터 밖에서 발생하는 문제를 점검하되, 최종 UI를 거치는 전체 흐름은 다시 검증한다.

## 2026-10-06 — 결정 4: 헤더의 불리언 멤버 타입

### 배경

사용자는 멀티플레이 기본 흐름 구현을 준비하면서 헤더의 불리언 선언에 `uint8`을 사용하고 문서에 명시하라고 지시했다. 이후 적용 범위를 멤버 변수로 한정했으며, `.cpp`의 지역 변수에는 `bool`을 허용했다.

### 결정

헤더의 클래스·구조체 불리언 멤버 변수만 `uint8`을 사용한다. 함수 반환값·매개변수와 `.cpp` 지역 변수는 `bool`을 유지한다. 엔진 오버라이드와 외부 인터페이스의 함수 시그니처도 원래 타입을 유지한다. 규칙 정본은 [Coding](Coding.md)이다.

### 트레이드오프

모든 위치에서 `bool`을 사용하는 대안보다 멤버 저장 타입과 함수 인터페이스를 구분한다. `uint8`은 정수 타입이므로 불리언 멤버에 저장하는 값을 0 또는 1로 제한해야 한다.

## 2026-10-06 — 결정 5: 실행 환경과 개별 재스폰

### 배경

사용자는 평소 작업은 Standalone에서 수행하고 서버 테스트는 Dedicated Server와 Listen Server에서 진행한다고 지정했다. 사망 처리는 사망한 플레이어만 개별 재스폰하는 안으로 구현하도록 지시했다.

### 결정

기본 흐름은 Standalone, Dedicated Server와 Listen Server에서 동작하도록 구현한다. 사망한 플레이어는 재도전 입력으로 시작 지점에 새 캐릭터를 생성하며 다른 플레이어의 진행은 유지한다. 결정 3의 초기 실행 계획을 이 방식으로 구체화한다. 최종 접속 인원과 협동·대전 규칙은 아직 미정이다.

사망과 캐릭터 생성은 서버가 결정한다. 서버가 없는 Standalone에서도 같은 권위 경로를 사용한다. 상세 설계와 검증 상태는 [MultiplayerFoundation](MultiplayerFoundation.md)이 소유한다.

### 트레이드오프

Standalone은 평소 반복 작업을 단순하게 하지만 복제와 원격 입력 문제를 드러내지 못한다. 두 서버 형태에서 별도 검증이 필요하다. 개별 재스폰은 생존자의 조작을 유지하지만 파티 전체 재시작이나 동료 부활 규칙은 포함하지 않는다.

## 2026-10-06 — 결정 6: C++ 선언과 정의 배치

### 배경

사용자는 헤더와 CPP 예시를 제시하며 코딩 문서에 형식을 정리하고 구현에도 적용하도록 지시했다. 부모 인터페이스, 클래스 자체 함수, 접근자·단순 검사, 에디터 전용 코드와 프로퍼티의 위치를 지정했다.

### 결정

헤더의 파일 범위 선언과 클래스 내부 영역, CPP 정의 순서는 [Coding](Coding.md)의 배치 규칙을 따른다. static 함수는 묶고, 단순 반환·설정·검사는 헤더에 정의한다. `UFUNCTION`과 프로퍼티는 주석을 포함한 선언 묶음 사이에 빈 줄을 둔다. 에디터 전용 영역에서는 함수와 프로퍼티를 함께 두되, UHT 제약에 따라 함수는 `WITH_EDITOR`, 리플렉션 데이터는 `WITH_EDITORONLY_DATA`로 감싼다.

현재 CCL 클래스에도 같은 형식을 적용한다. 이번 정리는 함수 동작과 접근 권한을 유지하며, 반환형이 `bool`이라는 이유만으로 일반 처리 함수를 단순 검사 그룹으로 옮기지 않는다.

### 트레이드오프

선언 종류와 역할별 위치가 일정해져 클래스 간 탐색이 쉬워진다. 관련된 일반 함수와 프로퍼티는 서로 떨어질 수 있다. 멤버 초기화 순서와 리플렉션 지정자를 보존하고 함수별 비교와 빌드로 형식 변경을 검증한다.

## 2026-10-06 — 결정 7: 멤버 변수의 빈 줄 조건

### 배경

사용자는 프로퍼티에 주석이나 `UPROPERTY`가 있을 때만 빈 줄을 두도록 지정했다.

### 결정

결정 6의 프로퍼티 간 빈 줄 규칙을 보완한다. 주석이나 `UPROPERTY`가 있는 선언 묶음은 앞뒤에 빈 줄 하나를 두고, 둘 다 없는 일반 멤버 변수끼리는 빈 줄 없이 이어 쓴다. 나머지 배치 규칙은 유지한다.

### 트레이드오프

일반 멤버 목록을 짧게 유지하면서 설명과 리플렉션 지정자가 있는 선언은 구분할 수 있다. 모든 멤버 사이의 간격은 같지 않다.

## 2026-10-06 — 결정 8: 회피·가드·패링 포함

### 배경

사용자는 일반 몹 한 종류와 최소 전투의 방어 방식에 대해 회피, 가드와 패링이 모두 필요하다고 명시했다.

### 결정

최소 전투에 회피, 가드와 패링을 모두 포함한다. 하나를 선택하고 나머지를 제외하는 범위로 축소하지 않는다. 세 행동의 역할, 입력, 수치와 공격별 대응 규칙은 [CombatFoundation](CombatFoundation.md)의 설계 초안에서 구체화한다. 이 결정은 세부 수치나 구현 완료를 뜻하지 않는다.

### 트레이드오프

적의 공격에 대응하는 선택이 늘어난다. 단일 방어 행동만 만드는 대안보다 애니메이션, 입력 충돌, 상태 전이와 네트워크 검증량이 늘어나므로 한 종류의 적과 기본 공격을 기준으로 세 방어 행동을 함께 확인한다.

## 2026-10-06 — 결정 9: 장르에 독립적인 베이스 시스템

### 배경

사용자는 HUD, Inventory, Item, Drop, Save/Load와 일반 전투 판정 등 베이스 작업을 특정 장르에 국한하지 않고 범용적으로 설계하라고 지정했다. ItemDefinition에 Fragment를 조합해 아이템을 정의하는 방식을 예로 들었다.

### 결정

베이스 시스템의 공통 책임과 데이터 흐름을 장르별 콘텐츠 규칙에서 분리한다. 정의 데이터, 개별 상태, 실행 기능과 표현을 구분하며 콘텐츠는 데이터·정책·기능 조합으로 연결한다. Item은 ItemDefinition과 Fragment 조합을 기준으로 설계한다. 원칙과 검토 기준의 정본은 [Coding](Coding.md)이다.

[CombatFoundation](CombatFoundation.md)의 일반 판정 기반에도 이 기준을 적용한다. 회피·가드·패링과 스태미나 규칙은 콘텐츠 계층에서 구성한다. 결정 8의 세 방어 행동 포함 범위는 유지한다. 이 결정은 게임의 장르·제작 범위를 바꾸거나 모든 장르의 기능을 미리 구현하라는 뜻이 아니다.

### 트레이드오프

장르 전용 구현보다 인터페이스, 데이터 검증과 연결 코드가 필요하다. 공통 계약과 확장 지점을 먼저 정하면 다른 콘텐츠를 추가할 때 기반 코드의 장르 분기를 줄일 수 있다. 필요한 기능부터 구현하되 제작 기간을 이유로 범용 설계 원칙을 생략하지 않는다.

## 2026-10-06 — 결정 10: UE5 신규·현행 시스템 우선

### 배경

사용자는 코딩 설계에서 정말 불합리한 경우가 아니면 UE5의 신규 시스템과 기능을 우선 사용하라고 지정했다. Nanite, World Partition, GAS와 Attribute를 예로 들었다.

### 결정

적용 대상에 맞는 UE5 신규·현행 시스템을 기본 선택으로 설계·구현한다. 기존 방식이나 자체 구현을 선택하는 예외에는 명확한 제약·검증 근거와 대안의 트레이드오프를 기록한다. GAS처럼 이전 버전부터 존재하는 현행 시스템도 포함한다. 원칙의 정본은 [Coding](Coding.md)이다.

최소 전투 설계는 GAS와 Attribute·AttributeSet을 기본 선택으로 구체화한다. 결정 9의 장르 독립 설계와 콘텐츠 분리 원칙도 함께 적용한다. 이 결정은 프로젝트 설정에서 모든 기능을 즉시 활성화하거나 실행 검증을 완료했다는 뜻이 아니다.

### 트레이드오프

엔진이 제공하는 기능과 통합 경로를 활용할 수 있는 대신 학습·구성 비용과 버전·플랫폼 제약을 확인해야 한다. 초기 설정의 편의만으로 자체 기반을 만들기보다 현행 시스템을 우선 사용하고, 요구에 부적합한 경우 근거를 남겨 대안을 선택한다.

## 2026-10-06 — 결정 11: 최소 전투 구현 범위와 ASC 수명

### 배경

회피·가드·패링을 포함하는 GAS 전투 초안의 구현 요청에 따라 ASC 소유자, 초기 표현과 방어 결과를 정해야 했다. 사용자는 PlayerState 소유, 마네킹·맨손, 가드 붕괴 공격 차단과 행동 중 카메라 방향을 선택하고 전체 구현 계획을 승인했다.

### 결정

플레이어 ASC는 PlayerState, 적 ASC는 적 Actor가 소유한다. 개별 재스폰은 플레이어 ASC와 능력을 유지하고 Avatar·현재 생명 효과·자원을 초기화한다. 최초 일반 몹과 기본 공격은 마네킹·맨손으로 구성한다. 가드가 붕괴하는 공격은 막고 이후 경직 중 공격에 피해를 받는다.

공격·가드·패링은 카메라의 수평 방향을 따르며 공격 방향은 유효 구간 시작에 고정한다. 평소에는 이동 방향을 따른다. 좌클릭 공격, 우클릭 유지 가드, Q 패링, Shift 회피를 사용한다. 적은 StateTree와 GAS를 연결한다. 별도 World Partition 전투장, 환경 Nanite, 스태미나 없는 표적과 네트워크 검증을 포함한다.

승인한 프로토타입 수치와 구현·검증 경계는 CombatFoundation이 소유한다. 이 결정은 최종 밸런스, 락온, 인벤토리·저장과 협동·대전 규칙을 확정하지 않는다.

### 트레이드오프

PlayerState 소유는 재스폰 후 능력 유지에 유리하지만 이전 생명의 효과와 콜백을 명시적으로 정리해야 한다. 전투 행동 중 카메라 방향을 쓰면 락온 없이 정면 방어를 조작할 수 있지만 방향 고정 시점과 회전 반응을 플레이로 확인해야 한다. 임시 마네킹 표현은 행동 검증을 시작하기에 적합하며 전용 전투 애니메이션의 품질을 대신하지 않는다.

### 트레이드오프

값 기반 Fragment는 선택 기능을 하나의 배열에서 편집할 수 있지만 이전 UObject 에셋의 변환과 파생 구조체 조회가 필요하다. 양손 장비는 항목 하나와 슬롯 두 개를 연결하므로 반환 공간과 중복 효과를 함께 검증해야 한다. 캐릭터 캡처는 실제 장비 표현을 공유하지만 화면을 열고 있는 동안 추가 렌더링 비용이 든다.

## 2026-10-09 — 결정 19: 자연 환경의 상호작용과 기능별 실험장

### 배경

사용자는 항성·행성·위성의 운동에서 시간·계절·날씨가 이어지고, 눈이 쌓여 사람이 지나간 길이 남으며 융해·유출·진흙·결빙·건조로 순환하는 환경을 요청했다. 영구 지형 변경을 허용하는 방향으로 범위를 확장하고 생태계·Agent의 생애 주기, 불과 공간 차폐, 직접 시험할 맵도 요구했다. 현재 계획을 노트북에서 실행할 수 있도록 문서화하고 업로드하도록 지시했다.

### 결정

처음은 한 행성 지상에서 플레이하고 다른 천체로 확장할 데이터 기반을 둔다. 서버 공통 시간에 천체·날씨·생태·Agent의 생애를 연결한다. 기존 Agent 코드의 60배속은 변경 가능한 실험 기본 후보로 두며 최종 게임 속도로 확정하지 않는다. 이동·전투 시간과 세계 경과 시간은 구분한다.

플레이어와 지정 사건의 굴착·성토는 영구 저장한다. 날씨에 의한 일상적인 영구 침식은 제외한다. 터널을 표현할 데이터 기반을 검토하되 초기 실험은 구덩이·수로·성토로 제한하고 핵심 마을·퀘스트·스폰 구역을 보호한다. 눈·물·충돌·AI 경로·식생은 변경 지형을 반영한다.

눈·물의 순환과 깊은 통과 흔적, 불·열·소화, 강수·일사·바람 차폐와 간단한 실내 환기를 기본 범위로 둔다. 생태계는 서식지·개체군·무리·개체를 나누고 Mass를 실행 수단으로 검토한다. 식물과 보이는 버섯은 상태를 가지며 보이지 않는 미생물·균은 부패 등을 위한 수치로만 존재한다. 일반 생물·주민의 생애를 시간에 연결하고 핵심 퀘스트 NPC의 자연 수명은 보호한다. 결정 18의 초기 Agent 계약에 대한 확장 계획이며 기존 구현 완료를 뜻하지 않는다.

기능별 구역을 가진 실험장과 격리 시나리오를 만들고 조작법·기대 결과·자동 판정·초기화를 제공한다. 전체 구현 순서, 소유권, 저장·네트워크 계약과 미확인 항목은 [EnvironmentPlan](EnvironmentPlan.md)이 소유한다. 클래스와 실험 수치는 검증할 후보이며 확정된 성능 사양이 아니다.

### 트레이드오프

영구 지형과 깊은 눈은 충돌·이동 예측·물질 보존·저장·복제 비용을 늘린다. 모든 생물을 개별 실행하거나 전체 월드를 정밀 물리로 계산하는 대신 활성 영역의 상세 상태와 먼 지역 집계를 연결한다. 공통 시간은 인과관계를 맞추지만 노화·날씨 속도와 이동 체감의 조정이 필요하다. 기존 RPG 흐름은 유지하며 전체 환경 확장의 기존 제작 기간 내 완료는 보장하지 않는다. 단계별 실험 결과로 표현 방식과 출시 포함 범위를 정한다.

## 2026-10-11 — 결정 21: 원격 플레이어의 서버 발급 신원과 복원 시 접속자 유지

### 배경

2026-10-11 전체 소스 검토에서 일반 플레이가 `UCCLPlayerPersistenceSubsystem::Bind`를 호출하지 않는 문제를 확인했다. 그래서 원격 플레이어의 세계 프로필이 저장되지 않았다. 음식을 든 미등록 플레이어가 있으면 세계 저장이 거부됐고, 맵 전환의 자동 저장은 그 실패를 확인하지 않았다. 사용자는 검토 결과의 결함과 의존 문제를 모두 올바른 방향으로 수정하라고 지시했다.

자동 연결을 추가하면 새 문제가 생긴다. 기존 세계 복원은 저장 본문에 프로필이 없는 등록 플레이어가 살아 있으면 거부했다. 접속하자마자 등록되는 플레이어가 생기면 그 뒤의 체크포인트 복원과 실험 초기화가 모두 실패한다.

### 결정

원격 플레이어의 신원은 서버가 발급한다. 첫 접속에서 서버는 256비트 무작위 비밀 키를 만들고 그 플레이어에게만 클라이언트 RPC로 전달한다. 클라이언트는 비밀 키를 서버 주소(`host:port`)별로 로컬 저장 슬롯 `CCL_ProfileKeys`에 보관한다. 재접속할 때는 로그인 옵션 `CCLProfile`로 제출한다. 서버는 비밀 키의 SHA-1 해시에 `profile:`을 붙여 프로필 식별 키로 쓴다. 그래서 세계 저장 파일에는 비밀 키 원문이 남지 않는다. 형식이 틀렸거나 연결할 수 없는 키, 그리고 이미 접속한 플레이어의 키에는 새 신원을 발급한다. 다른 연결의 프로필을 가져가지 못하게 하려는 것이다. 로컬 호스트는 기존처럼 개인 세션 기록이 소유한다.

세계 복원은 저장 이후에 접속한 등록 플레이어를 거부하지 않고 현재 상태로 유지한다. 유지한 플레이어의 계정이 복원된 원장에 없으면 마지막 잔액으로 다시 연다. 이 재개방은 복원 확정 단계의 명시적 호출만 수행한다. 조회·Tick·금화 변경은 사라진 계좌를 다시 만들지 않는다. 유지한 플레이어의 항목과 저장된 보관함의 아이템 GUID가 겹치거나 병합 결과가 검증을 통과하지 못하면 세계 변경 전에 복원을 거부한다.

### 트레이드오프

비밀 키는 엔진의 기본 네트워크 채널로 전달되며 이 채널은 암호화되지 않는다. 이 신원은 LAN과 직접 접속에서 재접속을 구분하는 장치다. 네트워크 공격자나 계정 도용을 막는 인증이 아니다. 클라이언트가 키 파일을 잃으면 새 신원으로 접속하며, 이전 프로필은 세계 기록에 남지만 다시 연결할 수 없다. 한 PC의 여러 클라이언트가 같은 서버에 접속하면 같은 슬롯을 쓴다. 두 번째 클라이언트는 새 신원을 받아 저장된 키를 덮어쓴다.

복원 때 접속자를 유지하면 그 플레이어의 상태는 저장 시각이 아니라 현재 시각에 머문다. 세계 전체를 한 시점으로 되돌리는 일관성 대신 접속을 유지한 채 체크포인트와 실험 초기화를 사용할 수 있는 쪽을 택했다. 접속자의 프로필을 강제로 초기화하거나 연결을 끊는 정책은 진행 손실을 만들기 때문에 선택하지 않았다.

## 2026-10-11 — 결정 22: 공용 시스템의 모듈 분리 방향과 KSI 이름

### 배경

결정 20은 공용화를 시스템 단위로 계획했지만 공통 접두사와 모듈·플러그인 구성을 정하지 않았다. 2026-10-11 사용자는 [FrameworkPlan](FrameworkPlan.md)을 여러 개인 UE5 프로젝트가 같이 쓰는 공용 인게임 Framework로서 검토해 달라고 요청했다. 이어서 플러그인을 제외하고 모듈로만 분리하는 방향의 평가를 요청했고, 공통 접두사로 자신의 이름 약자 `KSI`를 정했다. 실제 분리는 시작하지 않고 계획서만 개정하라고 지시했다.

검토에서 다음 사실을 확인했다. 네이티브 타입의 경로는 모듈 이름으로 정해진다. UBT는 모듈 순환을 오류로 처리한다. 2026-10-11 작업 트리에서 `UI/Core`와 `Map`은 다른 게임 폴더를 include하지 않았다. Items는 저장 참여 계약이 Environment 폴더에 있어 Environment를 include했다. 엔진 소스 경로와 측정값은 FrameworkPlan에 있다.

### 결정

공용 시스템은 프로젝트 안의 C++ 모듈로 분리한다. 플러그인은 현재 범위에서 제외하고, 다른 프로젝트와의 공유가 실제로 필요해지면 다시 검토한다. 공용 모듈은 `KSI{System}`, 공용 타입은 `KSI` 접두사를 쓴다. `Framework`는 모듈 이름에 붙이지 않고 문서에서 공용 시스템 전체를 부르는 이름 `KSI Framework`로만 쓴다. 게임 고유 모듈과 타입은 `CCL`을 유지한다.

이 결정은 결정 20의 `{Prefix}{System}Framework` 이름 형식을 대체한다. 결정 20에서 미정으로 남긴 공통 접두사와 모듈·플러그인 구성도 이 결정으로 정한다. 계획만 기록하고 착수 시점은 사용자가 정한다는 결정 20의 보류는 유지한다. 이 결정으로 코드 이동이나 이름 변경을 시작하지 않는다.

분리는 네 단계로 계획한다. 단계 1은 에디터 도구·UI 코어·지도, 단계 2는 공통 계약과 인벤토리, 단계 3-4는 전투·Agent·환경 계열이다. 단계 1-2는 착수하면 먼저 진행할 대상이다. 단계 1-2는 공유 수요가 없어도 CCL 안의 의존 방향을 바로잡기 때문이다. 단계 3-4는 정리 비용이 커서 재검토 계기가 생길 때 판단한다. 단계별 대상과 목표 계층은 FrameworkPlan이 소유한다.

### 트레이드오프

모듈만 쓰면 의존 방향을 빌드 도구가 강제하고 `.uplugin` 관리 없이 시작할 수 있다. 대신 모듈에는 Content 폴더와 활성화 설정이 없어 다른 프로젝트와 에셋을 함께 공유하기 어렵다. 공용 코드는 에셋을 직접 참조하지 않아야 하고, 머티리얼·FX와 묶인 환경 계열은 프로젝트마다 에셋을 둬야 한다. 다른 프로젝트에서 모듈을 사용하는 방법도 아직 정하지 않았다. 모듈 이름이 타입 경로를 정하므로, 나중에 같은 이름의 모듈을 플러그인으로 감싸도 리다이렉트를 다시 처리하지 않는다.

이름 약자 접두사는 엔진·외부 코드와 겹칠 가능성이 낮고 공용 코드의 출처를 드러낸다. 대신 이름만으로는 시스템의 뜻을 알 수 없다. `GameFramework`, `Common` 같은 일반 단어는 뜻이 드러나지만 엔진의 폴더·모듈·클래스 이름과 섞이므로 접두사로 쓰지 않았다.

### 결정

결정 23에서 검토 뒤 진행하기로 한 단계 2를 착수한다. `KSICore`는 저장 참여·이름 있는 구간 검증·시간 읽기와 실행 구간 값 계약을 소유한다. 구체 세계 시계와 환경 진행은 CCL에 남긴다. 검증 자료는 게임이 구현한 선택 문맥으로 전달하고 공용 헤더가 생활·표면 타입을 참조하지 않게 한다. 구간 등록 객체가 소멸하면 해당 검증 콜백도 해제한다.

`KSIInventory`는 기본 아이템 정의, Fragment 기반 확장 데이터, GUID·수량·슬롯, Fast Array 복제와 기본 보관 실행을 소유한다. 개별 확장 상태는 `FInstancedStruct`로 보관한다. `UCCLItemDefinition`과 `UCCLInventoryComponent`는 공용 타입을 상속하는 게임 어댑터로 유지한다. 음식·탄약 상태와 장비·전투 Fragment, 환경 관측과 기존 저장 변환은 CCL이 소유한다.

게임 어댑터의 네이티브 클래스 경로와 기존 세계·세션 저장 필드 형식을 유지한다. 공용 구간 계약은 기본 인벤토리의 별도 저장 파일을 자동으로 세계 저장에 연결하지 않는다. 구체 저장 참여자는 계속 CCL에서 등록한다. 기본 저장 API는 정의를 게임이 제공한 조회 함수로 해석하고, 확장 상태는 별도 직렬화 훅이 없으면 저장을 거부한다. 완료 판정과 실행 근거는 FrameworkPlan이 소유한다. 단계 3-4와 공용 저장소 배포는 착수하지 않는다.

### 트레이드오프

파생형 어댑터는 기존 게임 클래스·에셋과 저장 형식을 유지하면서 공용 모듈의 역방향 의존을 끊는다. 대신 공용 동작과 게임 확장을 각각 검증해야 하고, 확장 상태의 값 복사·직렬화 비용이 생긴다. 여러 기능을 전역 등록하는 방식보다 등록 수명과 조합 규칙은 적지만 게임마다 파생형의 확장 훅을 구현해야 한다. 이번 분리에서 성능 향상을 주장하지 않는다.

## 2026-10-12 — 결정 25: 공용 전투와 게임 정책의 분리

### 배경

사용자가 Framework 단계 2 검증·제출 이후 단계 3 구현과 검증·문서 정리·push를 지시했다. 적중 문맥에는 팀이, ASC에는 사망 태그가, 공통 효과 부여에는 게임 Magnitude 태그가 들어 있었다. 전투·능력·행동 코드를 그대로 옮기면 공용 모듈이 CCL 정책을 요구하므로 이 경계를 먼저 분리했다.

### 결정

결정 24의 단계 3 보류를 해제한다. `KSICombat`은 공격 식별·대상·거리·차폐·중복 검사, 적중 정책과 수신 계약, GAS 입력·부여·효과 적용, Source별 행동 수명을 소유한다. GameplayAbilities·GameplayTags·GameplayTasks를 필수 엔진 의존으로 둔다. CCL이나 다른 KSI 모듈은 요구하지 않는다.

피해·팀·스태미나·가드·패링·AttributeSet과 무기·탄약은 CCL이 소유한다. 발사 당시 팀은 게임 구조체를 FInstancedStruct 값으로 전달한다. UCCLCombatDefinition·UCCLAbilitySystemComponent·UCCLAbilitySet은 게임 파생형으로 유지하고 기존 에셋 경로를 보존한다. 옮긴 타입은 KSI 이름과 CoreRedirects를 사용한다. Source 행동 목록은 별도 복제하지 않으며 입력·능력 예측과 효과 복제는 GAS가 처리한다.

원본 에셋 로드, CCL 회귀와 패키지 실행에 더해, KSICombat만 복사한 별도 프로젝트에서 함정·표적·행동 수명을 검증했다. 검사 범위와 근거는 [FrameworkPlan](FrameworkPlan.md#단계-3-구현과-검증)이 소유한다. 단계 4와 공용 저장소 배포는 착수하지 않는다.

### 트레이드오프

GAS를 유지하면 기존 예측·태그·효과 수명을 재사용하고 게임 동작을 보존하기 쉽다. 대신 GAS가 없는 프로젝트에 KSICombat을 그대로 적용할 수 없다. 범용 효과 인터페이스를 따로 만들고 GAS 연결 모듈을 추가하는 대안은 공개 계약과 검증 조합이 늘어나므로 이번 분리에서는 선택하지 않았다.

게임 파생형과 값 문맥은 공용 모듈의 역방향 의존을 끊지만 게임이 공급할 정책과 자료를 별도로 검증해야 한다. ActionSet의 네이티브 클래스 이름이 달라져 이를 문자열 PrimaryAssetId로 저장하는 외부 사용자는 추가 변환이 필요하다. CCL의 기존 저장은 해당 식별자를 기록하지 않으며 저장 형식을 유지했다.
