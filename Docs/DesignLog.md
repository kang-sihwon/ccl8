# 설계 결정 이력

추가·번복 절차는 [WritingGuide](WritingGuide.md)를 따른다.

## 2026-10-05 — 결정 1: 제작 방향과 단기 콘텐츠 범위

### 배경

사용자는 CCL 신청 계획서에 소울라이크 RPG 제작을 이미 기재했다고 설명했다. 전체 작업 방향과 그래픽 스타일은 Orbis와 같게 유지하되 장기 프로젝트가 아닌 3-4개월 내 완성을 지시했다.

### 결정

소울라이크 RPG를 유지하고 마을 하나, 보스 하나, 보스에게 가는 동안 싸울 서로 다른 일반 몹 몇 종류, NPC 몇 명과 간단한 시나리오를 만든다. 그래픽 스타일은 Orbis를 기준으로 한다. 정확한 일반 몹·NPC 수와 세부 전투 규칙은 아직 결정하지 않았다.

범위 정본은 [Direction](Direction.md)이다. CCL 프로그램 기간 3개월과 제작 목표 3-4개월은 구분하며 실제 제출일은 미확인으로 남긴다.

### 트레이드오프

제한된 공간과 보스에 제작 시간을 집중할 수 있는 대신 세계의 규모와 콘텐츠 다양성은 작아진다. Orbis의 전체 장기 시스템을 먼저 구현하는 대안은 이번 기한과 충돌할 수 있으므로 개별 필요성을 검토한다.

## 2026-10-05 — 결정 2: AI 주도 제작과 사용자 검토

### 배경

초기 구성은 사용자가 게임 코드를 작성하고 AI가 설계·예시·리뷰를 제공하는 방식이었다. 사용자는 ccl8에서는 AI가 주도해서 작업하고 자신은 검토, 수정 사항과 방향 지시를 맡는다고 명시했다.

### 결정

AI가 합의된 제작 범위의 기획, 아트 제안, 게임 코드·설정·에셋 제작, 통합, 검증과 문서화를 주도한다. 사용자는 결과를 검토하고 방향과 수정 사항을 지시한다. 이 역할 분담은 초기 Guide·Coding·설계 스킬의 사용자 직접 구현 기본값을 대체한다.

AI는 합의된 범위 안의 통상적인 구현을 위해 매 파일마다 재승인을 요구하지 않는다. 검토 가능한 작업 단위로 결과, 검증과 미확인 사항을 제시한다. 방향과 범위 변경은 사용자 검토 대상으로 남긴다. 힌트 훈련은 요청할 때 적용한다.

이번 작업은 제작 방향과 지침의 문서화이며 UE 프로젝트나 게임 구현을 완료했다는 뜻은 아니다.

### 트레이드오프

사용자의 직접 구현 시간을 줄이고 AI가 작업을 이어갈 수 있다. 반면 사용자가 코드를 작성하며 얻는 학습과 세부 통제는 줄어들 수 있다. 작은 결과물 단위의 검토와 실제 실행 검증으로 진행 상황을 확인한다.

## 2026-10-05 — 결정 3: 멀티플레이 구현과 제작 순서

### 배경

사용자는 초기 코드 베이스 논의에서 이번 CCL에 멀티플레이를 구현한다고 명시했다. 전투, 성장 기능과 콘텐츠를 순차로 만드는 계획을 검토한 뒤, 처음에는 에디터에서 플레이하므로 시작 화면을 후반으로 미루자고 제안했다. 사용자는 이를 반영한 작업 순서의 문서 저장을 요청했다.

### 결정

멀티플레이 기본 흐름, 일반 몹 한 종류와 최소 전투, 보스 초안과 승리·종료 조건 순으로 게임을 연결한다. 이후 인벤토리·장비·능력치·스킬의 기능과 UI를 구현하고, 일반 몹·보스·NPC·상점·퀘스트·튜토리얼을 보강한다. 시작 화면·방 생성·접속 UI·세이브·로드·설정을 만든 뒤 최종 패키징과 전체 흐름 검증을 진행한다.

초기는 PIE로 테스트 맵에 직접 진입하고 서버·클라이언트 실행 설정으로 멀티플레이를 검증한다. 별도 프로세스 접속과 패키징 실행 확인도 초기 기본 흐름부터 보스 초안까지의 작업 중에 수행한다. 작업 순서와 완료 기준의 정본은 [StudyRoadmap](StudyRoadmap.md)이다.

멀티플레이 인원과 서버 형태 등 세부 요구는 [GameDesign](GameDesign.md)에 미정으로 남긴다. 월별 배분은 일정 초안이며 이번 결정은 구현 완료나 납기 확정을 뜻하지 않는다.

### 트레이드오프

시작 화면부터 만드는 대안보다 멀티플레이와 전투 흐름을 먼저 확인할 수 있다. 대신 실제 시작·접속 UI를 포함한 사용자 경험의 검증은 후반에 이뤄진다. 초기 별도 프로세스·패키징 확인으로 에디터 밖에서 발생하는 문제를 점검하되, 최종 UI를 거치는 전체 흐름은 다시 검증한다.

## 2026-10-06 — 결정 4: 헤더의 불리언 멤버 타입

### 배경

사용자는 멀티플레이 기본 흐름 구현을 준비하면서 헤더의 불리언 선언에 `uint8`을 사용하고 문서에 명시하라고 지시했다. 이후 적용 범위를 멤버 변수로 한정했으며, `.cpp`의 지역 변수에는 `bool`을 허용했다.

### 결정

헤더의 클래스·구조체 불리언 멤버 변수만 `uint8`을 사용한다. 함수 반환값·매개변수와 `.cpp` 지역 변수는 `bool`을 유지한다. 엔진 오버라이드와 외부 인터페이스의 함수 시그니처도 원래 타입을 유지한다. 규칙 정본은 [Coding](Coding.md)이다.

### 트레이드오프

모든 위치에서 `bool`을 사용하는 대안보다 멤버 저장 타입과 함수 인터페이스를 구분한다. `uint8`은 정수 타입이므로 불리언 멤버에 저장하는 값을 0 또는 1로 제한해야 한다.

## 2026-10-06 — 결정 5: 실행 환경과 개별 재스폰

### 배경

사용자는 평소 작업은 Standalone에서 수행하고 서버 테스트는 Dedicated Server와 Listen Server에서 진행한다고 지정했다. 사망 처리는 사망한 플레이어만 개별 재스폰하는 안으로 구현하도록 지시했다.

### 결정

기본 흐름은 Standalone, Dedicated Server와 Listen Server에서 동작하도록 구현한다. 사망한 플레이어는 재도전 입력으로 시작 지점에 새 캐릭터를 생성하며 다른 플레이어의 진행은 유지한다. 결정 3의 초기 실행 계획을 이 방식으로 구체화한다. 최종 접속 인원과 협동·대전 규칙은 아직 미정이다.

사망과 캐릭터 생성은 서버가 결정한다. 서버가 없는 Standalone에서도 같은 권위 경로를 사용한다. 상세 설계와 검증 상태는 [MultiplayerFoundation](MultiplayerFoundation.md)이 소유한다.

### 트레이드오프

Standalone은 평소 반복 작업을 단순하게 하지만 복제와 원격 입력 문제를 드러내지 못한다. 두 서버 형태에서 별도 검증이 필요하다. 개별 재스폰은 생존자의 조작을 유지하지만 파티 전체 재시작이나 동료 부활 규칙은 포함하지 않는다.

## 2026-10-06 — 결정 6: C++ 선언과 정의 배치

### 배경

사용자는 헤더와 CPP 예시를 제시하며 코딩 문서에 형식을 정리하고 구현에도 적용하도록 지시했다. 부모 인터페이스, 클래스 자체 함수, 접근자·단순 검사, 에디터 전용 코드와 프로퍼티의 위치를 지정했다.

### 결정

헤더의 파일 범위 선언과 클래스 내부 영역, CPP 정의 순서는 [Coding](Coding.md)의 배치 규칙을 따른다. static 함수는 묶고, 단순 반환·설정·검사는 헤더에 정의한다. `UFUNCTION`과 프로퍼티는 주석을 포함한 선언 묶음 사이에 빈 줄을 둔다. 에디터 전용 영역에서는 함수와 프로퍼티를 함께 두되, UHT 제약에 따라 함수는 `WITH_EDITOR`, 리플렉션 데이터는 `WITH_EDITORONLY_DATA`로 감싼다.

현재 CCL 클래스에도 같은 형식을 적용한다. 이번 정리는 함수 동작과 접근 권한을 유지하며, 반환형이 `bool`이라는 이유만으로 일반 처리 함수를 단순 검사 그룹으로 옮기지 않는다.

### 트레이드오프

선언 종류와 역할별 위치가 일정해져 클래스 간 탐색이 쉬워진다. 관련된 일반 함수와 프로퍼티는 서로 떨어질 수 있다. 멤버 초기화 순서와 리플렉션 지정자를 보존하고 함수별 비교와 빌드로 형식 변경을 검증한다.

## 2026-10-06 — 결정 7: 멤버 변수의 빈 줄 조건

### 배경

사용자는 프로퍼티에 주석이나 `UPROPERTY`가 있을 때만 빈 줄을 두도록 지정했다.

### 결정

결정 6의 프로퍼티 간 빈 줄 규칙을 보완한다. 주석이나 `UPROPERTY`가 있는 선언 묶음은 앞뒤에 빈 줄 하나를 두고, 둘 다 없는 일반 멤버 변수끼리는 빈 줄 없이 이어 쓴다. 나머지 배치 규칙은 유지한다.

### 트레이드오프

일반 멤버 목록을 짧게 유지하면서 설명과 리플렉션 지정자가 있는 선언은 구분할 수 있다. 모든 멤버 사이의 간격은 같지 않다.

## 2026-10-06 — 결정 8: 회피·가드·패링 포함

### 배경

사용자는 일반 몹 한 종류와 최소 전투의 방어 방식에 대해 회피, 가드와 패링이 모두 필요하다고 명시했다.

### 결정

최소 전투에 회피, 가드와 패링을 모두 포함한다. 하나를 선택하고 나머지를 제외하는 범위로 축소하지 않는다. 세 행동의 역할, 입력, 수치와 공격별 대응 규칙은 [CombatFoundation](CombatFoundation.md)의 설계 초안에서 구체화한다. 이 결정은 세부 수치나 구현 완료를 뜻하지 않는다.

### 트레이드오프

적의 공격에 대응하는 선택이 늘어난다. 단일 방어 행동만 만드는 대안보다 애니메이션, 입력 충돌, 상태 전이와 네트워크 검증량이 늘어나므로 한 종류의 적과 기본 공격을 기준으로 세 방어 행동을 함께 확인한다.

## 2026-10-06 — 결정 9: 장르에 독립적인 베이스 시스템

### 배경

사용자는 HUD, Inventory, Item, Drop, Save/Load와 일반 전투 판정 등 베이스 작업을 특정 장르에 국한하지 않고 범용적으로 설계하라고 지정했다. ItemDefinition에 Fragment를 조합해 아이템을 정의하는 방식을 예로 들었다.

### 결정

베이스 시스템의 공통 책임과 데이터 흐름을 장르별 콘텐츠 규칙에서 분리한다. 정의 데이터, 개별 상태, 실행 기능과 표현을 구분하며 콘텐츠는 데이터·정책·기능 조합으로 연결한다. Item은 ItemDefinition과 Fragment 조합을 기준으로 설계한다. 원칙과 검토 기준의 정본은 [Coding](Coding.md)이다.

[CombatFoundation](CombatFoundation.md)의 일반 판정 기반에도 이 기준을 적용한다. 회피·가드·패링과 스태미나 규칙은 콘텐츠 계층에서 구성한다. 결정 8의 세 방어 행동 포함 범위는 유지한다. 이 결정은 게임의 장르·제작 범위를 바꾸거나 모든 장르의 기능을 미리 구현하라는 뜻이 아니다.

### 트레이드오프

장르 전용 구현보다 인터페이스, 데이터 검증과 연결 코드가 필요하다. 공통 계약과 확장 지점을 먼저 정하면 다른 콘텐츠를 추가할 때 기반 코드의 장르 분기를 줄일 수 있다. 필요한 기능부터 구현하되 제작 기간을 이유로 범용 설계 원칙을 생략하지 않는다.

## 2026-10-06 — 결정 10: UE5 신규·현행 시스템 우선

### 배경

사용자는 코딩 설계에서 정말 불합리한 경우가 아니면 UE5의 신규 시스템과 기능을 우선 사용하라고 지정했다. Nanite, World Partition, GAS와 Attribute를 예로 들었다.

### 결정

적용 대상에 맞는 UE5 신규·현행 시스템을 기본 선택으로 설계·구현한다. 기존 방식이나 자체 구현을 선택하는 예외에는 명확한 제약·검증 근거와 대안의 트레이드오프를 기록한다. GAS처럼 이전 버전부터 존재하는 현행 시스템도 포함한다. 원칙의 정본은 [Coding](Coding.md)이다.

최소 전투 설계는 GAS와 Attribute·AttributeSet을 기본 선택으로 구체화한다. 결정 9의 장르 독립 설계와 콘텐츠 분리 원칙도 함께 적용한다. 이 결정은 프로젝트 설정에서 모든 기능을 즉시 활성화하거나 실행 검증을 완료했다는 뜻이 아니다.

### 트레이드오프

엔진이 제공하는 기능과 통합 경로를 활용할 수 있는 대신 학습·구성 비용과 버전·플랫폼 제약을 확인해야 한다. 초기 설정의 편의만으로 자체 기반을 만들기보다 현행 시스템을 우선 사용하고, 요구에 부적합한 경우 근거를 남겨 대안을 선택한다.

## 2026-10-06 — 결정 11: 최소 전투 구현 범위와 ASC 수명

### 배경

회피·가드·패링을 포함하는 GAS 전투 초안의 구현 요청에 따라 ASC 소유자, 초기 표현과 방어 결과를 정해야 했다. 사용자는 PlayerState 소유, 마네킹·맨손, 가드 붕괴 공격 차단과 행동 중 카메라 방향을 선택하고 전체 구현 계획을 승인했다.

### 결정

플레이어 ASC는 PlayerState, 적 ASC는 적 Actor가 소유한다. 개별 재스폰은 플레이어 ASC와 능력을 유지하고 Avatar·현재 생명 효과·자원을 초기화한다. 최초 일반 몹과 기본 공격은 마네킹·맨손으로 구성한다. 가드가 붕괴하는 공격은 막고 이후 경직 중 공격에 피해를 받는다.

공격·가드·패링은 카메라의 수평 방향을 따르며 공격 방향은 유효 구간 시작에 고정한다. 평소에는 이동 방향을 따른다. 좌클릭 공격, 우클릭 유지 가드, Q 패링, Shift 회피를 사용한다. 적은 StateTree와 GAS를 연결한다. 별도 World Partition 전투장, 환경 Nanite, 스태미나 없는 표적과 네트워크 검증을 포함한다.

승인한 프로토타입 수치와 구현·검증 경계는 CombatFoundation이 소유한다. 이 결정은 최종 밸런스, 락온, 인벤토리·저장과 협동·대전 규칙을 확정하지 않는다.

### 트레이드오프

PlayerState 소유는 재스폰 후 능력 유지에 유리하지만 이전 생명의 효과와 콜백을 명시적으로 정리해야 한다. 전투 행동 중 카메라 방향을 쓰면 락온 없이 정면 방어를 조작할 수 있지만 방향 고정 시점과 회전 반응을 플레이로 확인해야 한다. 임시 마네킹 표현은 행동 검증을 시작하기에 적합하며 전용 전투 애니메이션의 품질을 대신하지 않는다.

## 2026-10-06 — 결정 12: 코드 작업 후 프로젝트 파일 생성과 빌드

### 배경

사용자는 코드 작업이 완료되면 `GenerateProjectFiles.bat`을 실행하고 빌드까지 수행하는 규칙을 요청했다. 소스 작성, 프로젝트 파일 생성과 실제 빌드 성공을 구분해 완료 여부를 판단해야 한다.

### 결정

코드 작업의 최종 변경 상태에서 `CCL.uproject`를 대상으로 `GenerateProjectFiles.bat`을 실행한 다음 프로젝트를 빌드한다. 기본 검증 구성은 `CCLEditor Win64 Development`이며 별도로 지정한 작업 구성도 검증한다. 실패를 해결하지 못하면 검증 미완료로 보고하고 생성·빌드 결과를 각각 남긴다. 절차의 정본은 [Coding](Coding.md)이다.

### 트레이드오프

작은 코드 변경에도 프로젝트 파일 생성과 빌드 시간이 추가된다. 대신 새 파일·모듈 설정의 누락과 컴파일 오류를 코드 작업의 완료 전에 확인할 수 있다. 문서만 변경한 작업에는 적용하지 않는다.

## 2026-10-06 — 결정 13: 헤더 영역과 선언 묶음의 빈 줄

### 배경

사용자는 HealthSet 헤더 예시로 `GENERATED_BODY()` 뒤와 함수 영역 사이를 빈 줄 하나로 구분하고, 접근 지정자 바로 다음 선언은 붙이는 형식을 지정했다. 결정 7의 선언 묶음 규칙에서 접근 지정자와 만나는 위치를 명확히 해야 했다.

### 결정

결정 6과 결정 7을 보완해 헤더의 영역 경계에는 빈 줄 하나를 두고 접근 지정자와 첫 선언 묶음 사이에는 빈 줄을 두지 않는다. `UFUNCTION`·`UPROPERTY`와 대상 선언은 붙이며 각 선언 묶음 사이를 빈 줄 하나로 구분한다. 세부 기준과 예시는 [Coding](Coding.md)이 소유한다. 적용 시 함수 본문, 선언 순서와 접근 권한을 보존한다.

### 트레이드오프

영역 경계와 선언 묶음을 구분하기 쉬워지는 대신 기존 헤더에 빈 줄 변경이 생긴다. 기존 로컬 변경과 구분해 비교하고 프로젝트 파일 생성·빌드로 검증한다.

## 2026-10-06 — 결정 14: CPP 제어문과 처리 단계의 가독성

### 배경

사용자는 한 줄로 붙인 조건문과 실행문 때문에 CPP 코드의 가독성이 낮다고 지적했다. `UCCLDuelHitRule::Resolve`를 중괄호 블록으로 펼치고 판정 단계 사이에 빈 줄을 넣은 예시를 제시했다.

### 결정

CPP의 제어문은 단일 실행문도 중괄호로 감싸고 본문을 별도 줄에 쓴다. 독립된 검증·분기와 처리 단계 사이를 빈 줄 하나로 구분한다. 조건식, 실행 순서와 반환값을 보존하며 프로젝트 CPP에 같은 기준을 적용한다. 세부 기준과 예시는 [Coding](Coding.md)이 소유한다.

### 트레이드오프

짧은 제어문도 여러 줄을 차지하지만 분기의 실행 범위와 조기 반환을 확인하기 쉬워진다. 연속된 선언·호출마다 빈 줄을 넣지는 않고 같은 작업 단위로 묶는다.
