# 설계 결정 이력

추가·번복 절차는 [WritingGuide](WritingGuide.md)를 따른다.

## 2026-10-05 — 결정 1: 제작 방향과 단기 콘텐츠 범위

### 배경

사용자는 CCL 신청 계획서에 소울라이크 RPG 제작을 이미 기재했다고 설명했다. 전체 작업 방향과 그래픽 스타일은 Orbis와 같게 유지하되 장기 프로젝트가 아닌 3-4개월 내 완성을 지시했다.

### 결정

소울라이크 RPG를 유지하고 마을 하나, 보스 하나, 보스에게 가는 동안 싸울 서로 다른 일반 몹 몇 종류, NPC 몇 명과 간단한 시나리오를 만든다. 그래픽 스타일은 Orbis를 기준으로 한다. 정확한 일반 몹·NPC 수와 세부 전투 규칙은 아직 결정하지 않았다.

범위 정본은 [Direction](Direction.md)이다. CCL 프로그램 기간 3개월과 제작 목표 3-4개월은 구분하며 실제 제출일은 미확인으로 남긴다.

### 트레이드오프

제한된 공간과 보스에 제작 시간을 집중할 수 있는 대신 세계의 규모와 콘텐츠 다양성은 작아진다. Orbis의 전체 장기 시스템을 먼저 구현하는 대안은 이번 기한과 충돌할 수 있으므로 개별 필요성을 검토한다.

## 2026-10-05 — 결정 2: AI 주도 제작과 사용자 검토

### 배경

초기 구성은 사용자가 게임 코드를 작성하고 AI가 설계·예시·리뷰를 제공하는 방식이었다. 사용자는 ccl8에서는 AI가 주도해서 작업하고 자신은 검토, 수정 사항과 방향 지시를 맡는다고 명시했다.

### 결정

AI가 합의된 제작 범위의 기획, 아트 제안, 게임 코드·설정·에셋 제작, 통합, 검증과 문서화를 주도한다. 사용자는 결과를 검토하고 방향과 수정 사항을 지시한다. 이 역할 분담은 초기 Guide·Coding·설계 스킬의 사용자 직접 구현 기본값을 대체한다.

AI는 합의된 범위 안의 통상적인 구현을 위해 매 파일마다 재승인을 요구하지 않는다. 검토 가능한 작업 단위로 결과, 검증과 미확인 사항을 제시한다. 방향과 범위 변경은 사용자 검토 대상으로 남긴다. 힌트 훈련은 요청할 때 적용한다.

이번 작업은 제작 방향과 지침의 문서화이며 UE 프로젝트나 게임 구현을 완료했다는 뜻은 아니다.

### 트레이드오프

사용자의 직접 구현 시간을 줄이고 AI가 작업을 이어갈 수 있다. 반면 사용자가 코드를 작성하며 얻는 학습과 세부 통제는 줄어들 수 있다. 작은 결과물 단위의 검토와 실제 실행 검증으로 진행 상황을 확인한다.

## 2026-10-05 — 결정 3: 멀티플레이 구현과 제작 순서

### 배경

사용자는 초기 코드 베이스 논의에서 이번 CCL에 멀티플레이를 구현한다고 명시했다. 전투, 성장 기능과 콘텐츠를 순차로 만드는 계획을 검토한 뒤, 처음에는 에디터에서 플레이하므로 시작 화면을 후반으로 미루자고 제안했다. 사용자는 이를 반영한 작업 순서의 문서 저장을 요청했다.

### 결정

멀티플레이 기본 흐름, 일반 몹 한 종류와 최소 전투, 보스 초안과 승리·종료 조건 순으로 게임을 연결한다. 이후 인벤토리·장비·능력치·스킬의 기능과 UI를 구현하고, 일반 몹·보스·NPC·상점·퀘스트·튜토리얼을 보강한다. 시작 화면·방 생성·접속 UI·세이브·로드·설정을 만든 뒤 최종 패키징과 전체 흐름 검증을 진행한다.

초기는 PIE로 테스트 맵에 직접 진입하고 서버·클라이언트 실행 설정으로 멀티플레이를 검증한다. 별도 프로세스 접속과 패키징 실행 확인도 초기 기본 흐름부터 보스 초안까지의 작업 중에 수행한다. 작업 순서와 완료 기준의 정본은 [StudyRoadmap](StudyRoadmap.md)이다.

멀티플레이 인원과 서버 형태 등 세부 요구는 [GameDesign](GameDesign.md)에 미정으로 남긴다. 월별 배분은 일정 초안이며 이번 결정은 구현 완료나 납기 확정을 뜻하지 않는다.

### 트레이드오프

시작 화면부터 만드는 대안보다 멀티플레이와 전투 흐름을 먼저 확인할 수 있다. 대신 실제 시작·접속 UI를 포함한 사용자 경험의 검증은 후반에 이뤄진다. 초기 별도 프로세스·패키징 확인으로 에디터 밖에서 발생하는 문제를 점검하되, 최종 UI를 거치는 전체 흐름은 다시 검증한다.

## 2026-10-06 — 결정 4: 헤더의 불리언 멤버 타입

### 배경

사용자는 멀티플레이 기본 흐름 구현을 준비하면서 헤더의 불리언 선언에 `uint8`을 사용하고 문서에 명시하라고 지시했다. 이후 적용 범위를 멤버 변수로 한정했으며, `.cpp`의 지역 변수에는 `bool`을 허용했다.

### 결정

헤더의 클래스·구조체 불리언 멤버 변수만 `uint8`을 사용한다. 함수 반환값·매개변수와 `.cpp` 지역 변수는 `bool`을 유지한다. 엔진 오버라이드와 외부 인터페이스의 함수 시그니처도 원래 타입을 유지한다. 규칙 정본은 [Coding](Coding.md)이다.

### 트레이드오프

모든 위치에서 `bool`을 사용하는 대안보다 멤버 저장 타입과 함수 인터페이스를 구분한다. `uint8`은 정수 타입이므로 불리언 멤버에 저장하는 값을 0 또는 1로 제한해야 한다.

## 2026-10-06 — 결정 5: 실행 환경과 개별 재스폰

### 배경

사용자는 평소 작업은 Standalone에서 수행하고 서버 테스트는 Dedicated Server와 Listen Server에서 진행한다고 지정했다. 사망 처리는 사망한 플레이어만 개별 재스폰하는 안으로 구현하도록 지시했다.

### 결정

기본 흐름은 Standalone, Dedicated Server와 Listen Server에서 동작하도록 구현한다. 사망한 플레이어는 재도전 입력으로 시작 지점에 새 캐릭터를 생성하며 다른 플레이어의 진행은 유지한다. 결정 3의 초기 실행 계획을 이 방식으로 구체화한다. 최종 접속 인원과 협동·대전 규칙은 아직 미정이다.

사망과 캐릭터 생성은 서버가 결정한다. 서버가 없는 Standalone에서도 같은 권위 경로를 사용한다. 상세 설계와 검증 상태는 [MultiplayerFoundation](MultiplayerFoundation.md)이 소유한다.

### 트레이드오프

Standalone은 평소 반복 작업을 단순하게 하지만 복제와 원격 입력 문제를 드러내지 못한다. 두 서버 형태에서 별도 검증이 필요하다. 개별 재스폰은 생존자의 조작을 유지하지만 파티 전체 재시작이나 동료 부활 규칙은 포함하지 않는다.
