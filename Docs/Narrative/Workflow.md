# 서사 작업 절차

이 문서는 서사 항목을 조사에서 정본 반영까지 옮기는 절차를 소유한다. 정본([World](World.md), [Scenario](Scenario.md))에는 사용자가 범위를 명확히 승인한 내용만 들어가고, 검토 통과는 승인이 아니다. 서사 문서 사이의 소유는 [NarrativeConcept](../NarrativeConcept.md)가 정한다.

## 시작

1. 작성자는 [AGENTS.md](../../AGENTS.md), [WritingGuide](../WritingGuide.md), [Decisions](../Decisions.md), [NarrativeConcept](../NarrativeConcept.md), [CurrentWork](CurrentWork.md)를 순서대로 읽는다. 결정의 배경이 필요하면 `Docs/decisions/`에서 해당 번호의 파일을 연다.
2. 작성자는 현재 요청의 질문·범위·완료 조건을 정하고 CurrentWork의 담당 칸에 자기를 적는다.

이 절차는 Orbis에서 옮겨 ccl8에 맞춘 작업 방식의 하나다([Setup](../Setup.md)). Orbis의 서사 설정과, Orbis 절차에 있던 조사 작품 수 할당량과 일회성 예외는 ccl8에 적용하지 않는다. 할당량과 예외의 원래 내용은 이 저장소에 기록이 없다.

## 역할

| 역할 | 맡는 사람 | 하는 일 |
|---|---|---|
| 작성자 | 에이전트 하나(Claude Code 또는 Codex) | 조사, 후보 작성, 기록, 정본 반영 |
| 독립 검토자 | 작성자가 아닌 검토자. 읽기 전용 검토 에이전트나 사용자 | 출처, 논리, 다른 작품과의 유사성, 기존 정본과의 충돌 검토 |
| 승인자 | 사용자 | 후보 선택과 정본 반영 승인 |

- 한 항목의 작성자는 에이전트 하나가 맡는다. 다른 작성자의 진행 중 산출물을 임의로 덮지 않는다.
- 독립 검토는 `ccl8-narrative` 스킬에 적힌 읽기 전용 위임으로 할 수 있다. 검토 에이전트는 파일을 쓰지 않고 결과를 보고하며, 작성자가 그 결과를 Reviews에 옮긴다. 실제 독립 검토가 없으면 미검토라고 남긴다.
- 그 밖의 에이전트 생성이나 다른 세션에 메시지를 보내는 일은 [AGENTS.md](../../AGENTS.md)의 경계 절을 따른다. 이 절차 자체는 그 권한을 주지 않는다.
- 사용자가 범위를 명확히 승인한 내용만 World·Scenario에 반영한다. 호감 표현과 질문은 승인으로 간주하지 않는다.

## 조사와 후보

- 조사에서는 1차 출처를 우선하고 접근한 원문·확인 범위·추론을 구분한다.
- 다른 작품의 고유 이름, 문장, 설정 조합을 그대로 가져오지 않는다. 작동 방식과 반례를 분석하고, 인용은 짧게 하며 출처를 붙인다.
- 후보는 2-3개의 선택지, 제작 범위와 장단점으로 비교한다. 고유 설정과 장르 방향은 사용자와 정한다.

## 기록 위치

조사, 후보, 검토는 각 폴더에 기록한다. 파일 이름은 `YYYY-MM-DD-<english-kebab>.md`이고, 폴더는 첫 파일을 만들 때 만든다.

| 폴더 | 내용 | 항목이 끝난 뒤 |
|---|---|---|
| `Docs/Narrative/Research/` | 조사한 출처, 확인 범위, 분석 | 남긴다 |
| `Docs/Narrative/Drafts/` | 비교할 후보 | 채택한 문장은 정본으로, 비교와 기각 이유는 결정 파일로 옮긴 뒤 사용자 확인을 받아 지운다 |
| `Docs/Narrative/Reviews/` | 독립 검토 결과와 판정 | 결과를 결정 파일과 정본에 반영한 뒤 사용자 확인을 받아 지운다 |

## 단계와 판정

기본 단계는 `SCOPED → RESEARCHING → DRAFTING → REVIEW → DISCUSSION → APPROVAL_PENDING → CANONIZING → CLOSED`다. 간단한 작업은 필요한 단계만 사용하되 승인·검토 사실을 만들어내지 않는다. 각 단계에서 항목이 갖는 상태의 뜻은 [Glossary](Glossary.md)가 소유한다.

| 단계 | 뜻 | 항목 상태 |
|---|---|---|
| `SCOPED` | 질문과 범위를 정했고 조사는 시작하지 않았다 | 탐색 |
| `RESEARCHING` | 출처를 조사하고 있다 | 탐색 |
| `DRAFTING` | 후보를 쓰거나 고치고 있다 | 후보 |
| `REVIEW` | 독립 검토를 받고 있다 | 후보 |
| `DISCUSSION` | 사용자와 후보를 비교하고 있다 | 후보 |
| `APPROVAL_PENDING` | 사용자의 승인을 기다린다 | 승인 대기 |
| `CANONIZING` | 승인된 내용을 정본과 결정 파일에 반영하고 있다 | 승인 대기 |
| `CLOSED` | 항목이 끝났다 | 확정, 폐기 또는 대체됨 |
| `PARKED` | 재개 조건을 기다린다 | 보류 |
| `BLOCKED_SOURCE` | 근거가 부족해 멈췄다 | 보류 |

검토 결과는 아래 네 판정으로 구분한다. 검토 통과와 사용자 승인은 서로 다른 상태다.

| 판정 | 뜻 | 다음 단계 |
|---|---|---|
| `PASS` | 검토 기준을 통과했다. 사용자 승인이 아니다 | `DISCUSSION` |
| `CHANGES_REQUESTED` | 후보를 고쳐야 한다 | `DRAFTING`. 출처가 더 필요하면 `RESEARCHING` |
| `BLOCKED_SOURCE` | 판단할 근거가 부족하다 | 단계도 `BLOCKED_SOURCE`가 된다. 근거를 찾으면 `RESEARCHING` |
| `CANON_CONFLICT` | 기존 정본과 충돌한다 | `DISCUSSION`. 사용자가 후보를 고치기로 하면 `DRAFTING`, 정본을 바꾸기로 하면 그 변경을 승인 범위에 넣는다 |

사용자가 후보를 채택하지 않으면 작성자는 항목을 `CLOSED`로 끝내고 항목 상태를 폐기로 적는다.

## 승인과 정본 반영

1. 사용자가 승인하면 작성자는 [WritingGuide의 결정 기록 절차](../WritingGuide/DecisionRecords.md#결정을-기록하는-방법)로 결정 파일을 만든다. 머리말의 `topic`은 `서사`, `owners`는 반영할 World·Scenario 절이다. 본문 배경에는 승인 날짜, 사용자 발언의 직접 인용, 승인 범위를 적는다.
2. 작성자는 승인 범위의 내용만 World·Scenario의 "확정한" 절에 쓰고 항목 끝에 `근거: 결정 N` 링크를 붙인다.
3. 기존 확정 내용을 바꿀 때도 사용자 승인과 새 결정이 필요하다. 새 결정은 앞선 결정을 `supersedes`나 `supersedes_part`로 가리킨다. 바뀐 정본 항목은 새 결정을 근거로 달고, 옛 문장은 결정 파일과 Git이 맡는다. 옛 항목의 상태는 대체됨이다.
4. 반영 뒤 작성자는 승인 범위, 정본 문장, 결정 파일이 서로 맞는지와 게임 요구사항과 충돌하지 않는지 확인하고 `node Tools/Agent/decisions.cjs check`를 실행한다.
5. 작성자는 결과와 다음 행동을 CurrentWork에 남기고 담당을 해제한다.

## 인계

인계에는 완료 사실, 미승인 내용, 출처·검토 장애, 기다리는 결정과 다음 행동을 적는다. 문서 제출은 [VersionControl](../VersionControl.md)을 따른다. 코드·설정·에셋 변경은 이 절차에 포함되지 않는다.
