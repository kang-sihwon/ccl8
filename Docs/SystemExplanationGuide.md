# 시스템 학습 문서 작성 규칙

구현한 시스템을 교사가 학생에게 설명하듯 풀고, 실제 이전·현재 코드로 설계 선택의 이유를 가르치는 문서(`Docs/Learning/`)의 구성과 근거 기준을 소유한다. 문장·표기·검토는 [WritingGuide](WritingGuide.md)를 따른다.

독자는 C++ 개발 경험이 있지만 해당 UE 기능과 프로젝트 구조는 처음 볼 수 있다. 2026-10-09 사용자가 이 형식을 요청하고 [인벤토리 UI 예시](Learning/InventoryUI.md)를 승인했다. 그 예시에서 `SNew`의 뜻부터 확인해야 했으므로, 처음 나오는 엔진 문법은 코드 비교 전에 설명한다.

## 범위와 소유

기능 사양과 현재 검증 상태는 각 시스템의 Foundation 문서, 확정 결정과 당시 이유는 Decisions와 DesignLog가 소유한다. 학습 문서는 그 내용을 연결해 설명하며 새 게임 규칙을 확정하지 않는다.

학습 문서는 `Docs/Learning/<System>.md`에 두고 [문서 지도](README.md)에 등록한다. 시스템이 크면 독자가 동작 하나를 시작부터 끝까지 따라갈 수 있는 범위로 나누고, 상위 문서에서 읽는 순서와 시스템 사이의 관계를 안내한다.

쓰기 전에 독자, 학습 목표, 대상 기능, 비교 기준, 다루지 않을 범위를 정한다. 문서가 최신 상태를 설명하는지, 특정 커밋의 변화를 보존하는 기록인지도 정한다. 기준이 고정된 문서의 "현재"는 지정 커밋이며 이후 `HEAD`와 같다고 보장하지 않는다.

## 설명 방식

- 첫 문단에서 무엇이 달라졌고 무엇을 이해하게 되는지 밝힌다. 이어서 실제 플레이 상황과 해결할 문제를 설명한다.
- UE 전용 매크로, 타입, 수명, 입력·복제 계약은 처음 나올 때 뜻과 목적을 설명한다. 일반 C++ 문법은 생략할 수 있다.
- 코드 앞에서 그 코드가 필요한 상황을, 코드 뒤에서 실행 순서와 책임을 설명한다. 식별자를 한국어로 옮겨 나열하는 것은 설명이 아니다.
- UObject의 생성·참조와 Slate의 공유 포인터처럼 다른 수명 모델이 섞이면 차이를 설명한다. 소유자 지정만으로 모든 참조와 정리가 보장된다고 단정하지 않는다.
- 공용 함수 호출로 코드가 짧아졌으면 내부에서 실제 처리를 맡는 객체까지 추적한다. `OpenView` 한 줄에서 생성·입력·해제 설명을 끝내지 않는다.
- 정상 실행과 함께 실패, 종료, 재사용 경로를 설명하고 서버 권한, 로컬 표현, 월드·플레이어 수명처럼 변경에 영향을 준 경계를 밝힌다.
- 기존 방식이 유효했던 범위와 새 방식의 비용을 함께 쓴다. 추상화나 클래스 증가는 개선의 증거가 아니다.
- UE4에도 있던 기능과 UE5에서 달라진 기능을 구분한다. 프로젝트의 리팩터링을 엔진 버전 변경으로 설명하지 않는다.

## 한 장의 기본 구성

아래 순서를 기본으로 쓴다. 절을 합치거나 나눌 수 있지만 해당하는 항목은 빠뜨리지 않는다.

| 순서 | 내용 | 독자가 이해해야 할 것 |
|---|---|---|
| 1 | 비교 기준 | 브랜치·커밋·대상 파일과 "현재"의 의미 |
| 2 | 해결할 문제 | 플레이 상황에서 필요한 동작과 제약 |
| 3 | 필요한 개념 | 이후 코드에 나오는 엔진 문법과 용어 |
| 4 | 이전 구현 | 실제 코드의 실행 흐름과 책임 배치 |
| 5 | 변경 계기 | 추가 요구, 한계, 기록된 결정 이유 |
| 6 | 현재 구현 | 같은 동작의 현재 코드와 달라진 책임 |
| 7 | 내부 연결 | 호출 대상에서 실제 생성·처리로 이어지는 경로 |
| 8 | 입력·권한·수명 | 시스템에 해당하는 경계와 정책 |
| 9 | 종료와 실패 | 닫기, 해제, 취소, 재사용과 실패 처리 |
| 10 | 대안과 비용 | 선택한 방식의 이점과 감수한 제약 |
| 11 | 확인 방법 | 재현 상황, 기대 결과, 실제 확인 범위 |
| 12 | 이해 확인 | 이유를 설명하게 하는 질문과 해설 |

최초 구현은 이전 코드가 없다는 사실을 밝히고 문제에서 구현으로 이어지는 과정을 설명한다. 비교 항목을 채우려고 가상의 이전 코드를 만들지 않는다. 네트워크가 없는 기능에는 서버 권한 절을 두지 않는다.

## Git 이력과 변경 이유

작성 시점의 로컬 브랜치, 원격 추적 브랜치, 작업 트리 상태를 확인한다. 원격 추적 정보만 봤으면 원격 서버의 최신 상태를 확인했다고 쓰지 않는다. 브랜치가 하나면 커밋 전후를 비교하고 확인 범위를 적는다. 이력을 보려고 브랜치를 전환하거나 작업 트리를 덮어쓰지 않는다.

브랜치가 여럿이면 각 브랜치의 역할과 분기·병합 관계를 먼저 확인한다. 병렬 브랜치를 시간순 단계처럼 나열하지 않는다. 필요하면 공통 조상, 변경 도입 커밋, 병합 뒤 상태를 비교한다. 모든 커밋 대신 책임·계약이 바뀐 지점을 고른다.

비교 기준에는 브랜치명과 해석 가능한 커밋을 함께 적는다. 근거 표나 비교 기준 절에 전체 커밋 해시를 두고 본문은 짧은 해시를 쓸 수 있다. 이전·현재 코드의 파일과 함수도 적는다. 미커밋 작업 트리를 썼다면 커밋 코드와 구분한다.

변경 사실은 diff와 실제 코드로 확인한다. 당시 선택 이유는 결정 기록, 커밋 본문처럼 확인 가능한 근거로 쓴다. 코드에서 분석한 장단점은 분석이라고 밝히고, 이유가 기록되지 않았으면 "당시 이유 미기록"이라고 쓴다. 설명용 가정과 실제 버그 기록을 구분한다.

학습 문서는 이전·현재 비교가 주제이므로 변경 전 동작과 커밋을 본문에 담는다. 이 예외는 비교 학습에 필요한 이력에만 적용하며 사양·절차 문서에 작업 이력을 붙이는 근거가 아니다.

## 코드와 출처

프로젝트 코드는 Graft로 먼저 찾고, 빠지거나 불완전하면 실제 소스로 확인한다. 엔진 동작은 엔진 Graft와 실제 설치본의 소스로 확인한다. 엔진 인덱스의 이름만으로 소스 버전을 단정하지 않고, 확인한 설치본 버전과 프로젝트 커밋을 구분해 적는다.

- 전후 코드는 같은 동작을 비교한다. 열기뿐 아니라 변경 이유에 해당하는 입력·닫기·실패 처리도 보여 준다.
- 실제 코드 발췌, 생략·줄바꿈한 코드, 설명용 의사 코드를 구분해 표시한다.
- 코드 묶음마다 기준 커밋, 저장소 상대 경로, 함수나 심볼을 적는다. 파일 전체 대신 주장에 필요한 범위를 싣는다.
- 생략한 검사와 실패 경로를 밝히고, 생략 때문에 권한·수명 계약이 달라 보이지 않는지 확인한다.
- 새 추상화 안에 기존 기술이 남아 있으면 함께 설명한다. 호출 위치가 바뀐 것을 기술 제거로 쓰지 않는다.
- 코드 블록의 C++ 식별자와 타입을 보존한다. 경로는 저장소 상대 경로나 `<Engine>` 같은 자리표시자로 쓴다.

Mermaid는 객체 관계나 호출 순서를 이해하는 데 도움이 될 때 쓴다. 클래스 관계는 `classDiagram`, 처리 순서는 흐름도다. 그림에서 뺀 검증·실패 경로가 있으면 밝히고, 그림만으로 설명을 대신하지 않는다.

## 검증과 이해 확인

확인 방법은 상황과 기대 결과를 짝지어 쓴다. 실제로 실행한 검사는 조건과 근거를 남기고, 기존 문서의 검사 기록을 읽은 것과 이번에 새로 실행한 것을 구분한다. 코드가 있음, 빌드 성공, 게임 실행 성공은 서로 다른 상태다.

이해 확인 질문은 "어떤 함수를 썼는가"보다 "왜 이 책임을 옮겼는가", "언제 해제해야 하는가", "대안에는 어떤 비용이 있는가"를 묻는다. 자습할 수 있게 답과 설명을 함께 둔다. 문서를 읽었다는 사실로 사용자의 학습 성취를 기록하지 않는다.

## 저장 전 점검

1. 처음 읽는 사람이 앞선 대화 없이 문제와 변경 이유를 따라갈 수 있는지 확인한다.
2. 처음 나오는 엔진 용어를 설명했는지, 공용 호출 뒤의 실제 처리까지 연결했는지 확인한다.
3. 비교 커밋과 코드 발췌를 대조하고, 남은 기존 구현과 새 책임을 구분했는지 확인한다.
4. 기록된 이유, 분석, 가정, 미확인이 섞이지 않았는지 확인한다.
5. 대안의 비용과 정상·실패·종료 경로를 다뤘는지 확인한다.
6. 코드 경로와 문서 링크를 따라가 보고 실행 검증의 범위를 대조한다.
7. WritingGuide의 검토 순서로 문체, 맞춤법, 표기, 기술 문서 품질을 검토한다.

전체 적용 예시는 [인벤토리 UI: 화면 생성과 입력 관리를 분리한 이유](Learning/InventoryUI.md)다.
