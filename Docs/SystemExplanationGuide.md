# 시스템 학습 문서 작성 규칙

구현한 시스템을 교사가 학생에게 설명하듯 풀어 쓰고, 실제 이전·현재 코드로 설계 선택의 이유를 가르치는 문서에 적용한다. 독자는 C++ 개발 경험이 있지만 해당 UE 기능과 프로젝트 구조는 처음 접할 수 있다고 가정한다. 공통 문장·표기·검토 기준은 [WritingGuide](WritingGuide.md)를 따른다.

2026-10-09 사용자는 시스템별 구현 이유와 Git 이력의 전후 코드를 함께 설명하는 형식을 요청하고 [인벤토리 UI 예시](Learning/InventoryUI.md)를 승인했다. 예시에서 `SNew`의 뜻을 먼저 확인해야 했던 상황을 반영해, 처음 등장하는 엔진 문법을 설명한 뒤 코드를 비교하도록 한다.

## 적용 범위와 소유

이 문서는 학습 해설의 구성과 근거 기준을 소유한다. 기능 사양과 현재 검증 상태는 각 시스템의 Foundation 문서, 확정 결정과 당시 이유는 Decisions와 DesignLog가 소유한다. 학습 문서는 그 내용을 연결해 설명하며 별도의 게임 규칙을 확정하지 않는다.

학습 문서는 `Docs/Learning/<System>.md`에 둔다. 새 문서는 [Guide](Guide.md)의 문서 지도에 등록한다. 한 시스템이 너무 크면 독자가 하나의 동작을 시작부터 종료까지 따라갈 수 있는 범위로 나누고, 상위 문서에서 읽는 순서와 시스템 사이의 관계를 안내한다.

작성 전에 독자, 학습 목표, 대상 기능, 비교 기준, 다루지 않을 범위를 작업 메모에서 정한다. 문서 전체가 최신 상태를 설명하는지, 특정 커밋의 변화를 보존하는 학습 기록인지 구분한다. 기준이 고정된 예시의 ‘현재’는 지정 커밋을 뜻하며 이후 HEAD와 같다고 보장하지 않는다.

## 설명 방식

- 시작 문단에서 무엇이 달라졌고 무엇을 이해할 수 있는지 밝힌다. 이어서 실제 플레이 상황과 해결해야 할 문제를 설명한다.
- C++ 문법은 독자의 경험에 맞게 생략할 수 있지만 UE 전용 매크로, 타입, 수명, 입력·복제 계약은 처음 등장할 때 뜻과 사용 목적을 설명한다. `SNew`를 안다고 가정하고 구조 비교를 시작하지 않는다.
- 코드 전에 그 코드가 필요한 상황을 설명하고, 코드 뒤에서 실행 순서와 책임을 풀어 쓴다. 식별자를 한국어로 번역해 나열하는 것으로 설명을 대신하지 않는다.
- UObject의 생성·참조와 Slate의 공유 포인터처럼 서로 다른 수명 모델이 섞이면 차이를 설명한다. 소유자 지정만으로 모든 참조·정리가 보장된다고 단정하지 않는다.
- 공용 함수 호출로 코드가 짧아졌다면 내부에서 어떤 객체가 실제 처리를 맡는지도 추적한다. `OpenView` 한 줄만 보여주고 생성·입력·해제 설명을 끝내지 않는다.
- 정상 실행과 함께 실패, 종료, 재사용 경로를 설명한다. 서버 권한, 로컬 표현, 월드·플레이어 수명처럼 해당 변경에 영향을 준 경계를 밝힌다.
- 기존 방식의 유효했던 범위와 새 방식의 비용을 함께 설명한다. 추상화나 클래스 증가 자체를 개선의 증거로 삼지 않는다.
- UE4에도 있던 기능과 UE5에서 달라진 기능을 구분한다. 프로젝트의 자체 리팩터링을 엔진 버전 변경으로 설명하지 않는다.

## 한 장의 기본 구성

아래 순서를 기본으로 사용한다. 학습에 도움이 되면 절을 합치거나 나누되, 해당하는 항목을 빠뜨리지 않는다.

| 순서 | 내용 | 독자가 이해해야 할 것 |
|---|---|---|
| 1 | 비교 기준 | 브랜치·커밋·대상 파일과 ‘현재’의 의미 |
| 2 | 해결할 문제 | 플레이 상황에서 필요한 동작과 제약 |
| 3 | 필요한 개념 | 이후 코드에 나오는 엔진 문법과 용어 |
| 4 | 이전 구현 | 실제 코드의 실행 흐름과 책임 배치 |
| 5 | 변경 계기 | 추가 요구, 한계, 기록된 결정 이유 |
| 6 | 현재 구현 | 같은 동작의 현재 코드와 달라진 책임 |
| 7 | 내부 연결 | 호출 대상에서 실제 생성·처리로 이어지는 경로 |
| 8 | 입력·권한·수명 | 시스템에 해당하는 경계와 정책 |
| 9 | 종료와 실패 | 닫기, 해제, 취소, 재사용과 실패 처리 |
| 10 | 대안과 비용 | 선택한 방식의 이점과 감수한 제약 |
| 11 | 확인 방법 | 재현 상황, 기대 결과, 실제 확인 범위 |
| 12 | 이해 확인 | 이유를 설명하게 하는 질문과 해설 |

이전 코드가 없는 최초 구현은 그 사실을 밝히고 문제에서 구현으로 이어지는 과정을 설명한다. 비교 항목을 채우려고 가상의 이전 코드를 만들지 않는다. 네트워크가 없는 기능에 서버 권한 절을 억지로 추가하지 않는다.

## Git 이력과 변경 이유

작성 시점에 확인 가능한 로컬 브랜치, 원격 추적 브랜치, 작업 트리 상태를 확인한다. 원격 추적 정보만 확인했으면 원격 서버의 최신 상태까지 확인한 것처럼 쓰지 않는다. 브랜치가 하나라면 커밋 전후 비교를 사용하고 확인 범위를 명시한다. 이력 확인만을 위해 브랜치를 전환하거나 작업 트리를 덮어쓰지 않는다.

브랜치가 여러 개일 때는 각 브랜치의 역할과 분기·병합 관계를 먼저 확인한다. 병렬로 진행된 브랜치를 시간순의 이전·현재 단계처럼 나열하지 않는다. 필요한 경우 공통 조상, 변경 도입 커밋, 병합 후 상태를 비교한다. 모든 커밋 목록 대신 시스템의 책임·계약이 바뀐 의미 있는 지점을 고른다.

비교 기준에는 브랜치명과 해석 가능한 커밋을 함께 적는다. 문서의 근거 표 또는 비교 기준 절에 전체 커밋 해시를 보관하고 본문은 짧은 해시를 사용할 수 있다. 이전·현재 코드의 파일과 함수도 표시한다. 작업 트리의 미커밋 내용을 사용했다면 커밋 코드와 구분한다.

변경의 사실은 diff와 실제 코드로 확인한다. 당시 선택 이유는 결정 기록, 커밋 본문 등 확인 가능한 근거를 사용한다. 코드에서 분석한 장단점은 분석이라고 밝히고, 당시 이유가 기록되지 않았으면 ‘당시 이유 미기록’이라고 쓴다. 설명용 가정은 실제 버그 발생 기록과 구분한다.

이 학습 형식에서는 이전·현재 비교가 본문 주제이므로 변경 전 동작과 커밋을 설명할 수 있다. 이 예외는 비교 학습에 필요한 이력에 한정하며, 다른 사양·절차 문서에 작업 전달 이력을 붙이는 근거가 되지 않는다.

## 코드와 출처

프로젝트 코드는 Graft를 먼저 사용하고 누락되거나 불완전하면 실제 소스로 확인한다. 엔진 동작은 엔진 Graft와 실제 설치본의 소스로 확인한다. 엔진 인덱스의 이름만으로 소스 버전을 단정하지 않으며 확인한 설치본 버전과 프로젝트 커밋의 역할을 구분한다.

- 전후 코드는 같은 동작을 비교한다. 열기뿐 아니라 변경 이유에 해당하는 입력·닫기·실패 처리도 보여준다.
- 실제 코드 발췌, 생략·줄바꿈한 코드, 설명용 의사 코드를 명시적으로 구분한다. 의사 코드를 실제 구현처럼 제시하지 않는다.
- 각 코드 묶음에 기준 커밋, 저장소 상대 경로, 함수 또는 심볼을 연결한다. 긴 파일 전체 대신 주장에 필요한 범위를 싣는다.
- 생략한 검사와 실패 경로를 밝힌다. 생략으로 권한·수명 계약이 달라 보이지 않는지 확인한다.
- 새 추상화 내부에 기존 기술이 남아 있으면 함께 설명한다. 호출 위치가 바뀐 것을 기술이 제거된 것으로 표현하지 않는다.
- 코드 블록은 C++ 식별자와 타입을 보존한다. 공유 문서의 경로는 저장소 상대 경로 또는 `<Engine>` 같은 자리표시자를 사용한다.

Mermaid는 객체 관계나 호출 순서를 이해하는 데 도움이 될 때 사용한다. 클래스 관계는 `classDiagram`, 처리 순서는 흐름도로 구분한다. 그림에서 생략한 검증·실패 경로가 있으면 밝히고, 다이어그램만으로 설명을 대신하지 않는다.

## 검증과 이해 확인

확인 방법은 상황과 기대 결과를 대응시킨다. 실제 실행한 검사는 조건과 근거를 남기고, 기존 문서의 검사 기록을 읽은 경우와 이번 작성 중 새로 실행한 경우를 구분한다. 코드가 존재하는 것, 빌드 성공, 게임 실행 성공을 서로 다른 상태로 취급한다.

이해 확인은 ‘어떤 함수를 썼는가’보다 ‘왜 이 책임을 옮겼는가’, ‘언제 해제해야 하는가’, ‘대안에는 어떤 비용이 있는가’를 묻는다. 자습할 수 있도록 답과 설명을 함께 둔다. 문서를 읽었다는 사실만으로 사용자의 학습 성취를 기록하지 않는다.

## 저장 전 점검

1. 처음 읽는 사람이 앞선 대화 없이 문제와 변경 이유를 따라갈 수 있는지 확인한다.
2. 처음 등장하는 엔진 용어를 설명했는지, 공용 호출 뒤의 실제 처리까지 연결했는지 확인한다.
3. 비교 커밋과 코드 발췌를 대조하고, 남아 있는 기존 구현과 새 책임을 정확히 구분한다.
4. 기록된 이유, 분석, 가정, 미확인 상태가 섞이지 않았는지 확인한다.
5. 대안의 비용과 정상·실패·종료 경로를 확인한다.
6. 코드 경로와 문서 링크를 따라가고, 실행 검증의 범위를 대조한다.
7. WritingGuide의 검토 순서로 문체·맞춤법·표기와 기술 문서 품질을 검토한다.

전체 적용 예시는 [인벤토리 UI: 화면 생성과 입력 관리를 분리한 이유](Learning/InventoryUI.md)에 있다.
