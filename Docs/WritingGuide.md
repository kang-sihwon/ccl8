# ccl8 문서 작성 가이드

저장소에서 읽히는 글을 쓰고 고칠 때의 기준이다. 대상은 `README.md`, `AGENTS.md`, `CLAUDE.md`, `GLOSSARY.md`, `Docs/`의 Markdown 문서, 검토 보고서, 커밋 메시지, 스킬 문서다. 기준 독자는 며칠 뒤 다른 기기에서 앞선 대화 없이 처음 읽는 사람과 에이전트다.

## 기본 원칙

- 결론을 먼저 쓴다. 문서, 절, 문단 모두 결과부터 적고 과정은 뒤에 둔다.
- 앞선 대화를 가리키는 표현은 구체적인 문서, 결정, 사건으로 바꾼다.
- 한 문장에는 중심 판단 하나를 담는다. 조건, 근거, 결과가 길게 이어지면 인과를 유지한 채 문장을 나눈다.
- 사실, 분석, 추론, 미확인을 구분한다. 문장을 다듬을 때 가능성을 단정으로 바꾸거나 원문에 없던 이유를 넣지 않는다.
- 결정과 수치에는 문서에 남은 근거를 붙인다. 근거가 없으면 미기록 또는 미확인이라고 쓴다.
- 비유를 쓰면 실제로 무엇이 바뀌고 어떤 문제가 생기는지 이어서 쓴다.

## 제목과 문단

- 제목은 찾기 쉬운 짧은 명사구로 쓴다.
- 본문은 주어와 서술어가 분명한 완결문으로 쓴다. 관계를 명사 나열이나 화살표·등호로 대신하지 않는다.
- 한 문단은 주제 하나를 다룬다. 배경, 판단, 근거, 후속 조치가 다른 주제면 문단을 나눈다.
- 같은 설명은 소유 문서 한 곳에만 쓴다. 다른 문서는 그 문서를 연결하고 필요한 요약만 둔다.
- 다른 문서가 링크하는 제목은 앵커가 바뀌므로 고치기 전에 링크를 찾아 함께 바꾼다.

## 목록과 표

- 절차 목록의 각 단계는 누가 무엇을 하는지 드러나는 문장으로 쓴다.
- 상태, 이름, 수치, 짧은 분류값은 명사구로 적는다.
- 표의 한 셀에는 판단 하나를 둔다. 길어지면 표 아래에서 설명한다.
- 코드, 명령, 경로, URL, 해시는 인라인 코드나 코드 블록으로 쓴다.
- 클래스 다이어그램은 Mermaid `classDiagram` 코드 블록으로 쓴다.

## 용어와 표기

- 코드, API, 클래스명, 파일명, 명령, 상태값, 스키마 키, 문서 ID, 작품 고유명사는 원래 표기를 유지한다.
- 여러 문서에 걸친 시스템·제작 용어는 [GLOSSARY](../GLOSSARY.md), 서사 용어는 [서사 용어](Narrative/Glossary.md)가 소유한다. 그 밖의 프로젝트 용어는 처음 등장할 때 뜻을 설명하고 문서 안에서 같은 표기를 쓴다.
- ID를 처음 쓸 때는 `세계의 공간 구성을 정하는 항목(AX-05)`처럼 뜻을 함께 쓴다.
- 일반 문장의 영어는 한국어로 쓴다. `claim`은 주장, `coverage`는 확인 범위, `mechanism`은 작동 방식이나 구조, `cutoff`는 확인 기준일, `batch`는 작업 묶음이나 차수, `downstream`은 후속 항목이다. `gameplay`는 조작과 규칙이면 게임플레이, 진행 과정이면 게임 진행이다.
- 절차의 상태값이나 필드 이름인 영어(`canon`, `writer`, `reviewer`, `PASS` 등)는 그대로 둔다.
- 범위는 `1-3`, `단계 4-13`처럼 하이픈, 근사값은 `약 5MB`, 이름 접미사는 `...Rad`로 쓴다. 물결표(`~`)는 GitHub가 취소선으로 해석해 문단이 깨지므로 쓰지 않는다. VS Code 미리보기는 정상으로 보이므로 판정 기준은 GitHub 렌더링이다.
- 문장 부호는 쉼표, 마침표, 괄호를 쓴다. em dash는 결정 파일의 제목 형식(`# 날짜 — 결정 N: 제목`)에만 쓴다.

## 보존해야 하는 기록

- 직접 인용문, 실행한 명령, 실제로 쓴 프롬프트, URL, SHA-256, 출처 원문은 표현을 고치지 않는다.
- 과거 결정과 검토 기록의 날짜, 판정, 불확실성은 유지한다. 문장만 읽기 쉽게 고칠 수 있다.
- 현행 경로는 최신값으로 바꾸고, 과거 이동 기록은 날짜와 함께 남긴다.

## 문서의 종류와 소유

문서를 쓰기 전에 종류를 정한다. 종류가 수정 규칙을 정한다.

| 종류 | 예 | 수정 규칙 |
|---|---|---|
| 규범 | `AGENTS.md`, `Docs/Coding.md`, 이 문서 | 코드나 작업이 규칙을 어기면 규칙을 낮추지 않고 위반을 기록한다 |
| 사양 | `*Foundation.md`, `Environment*.md`의 시스템 문서 | 확정 수치와 인터페이스 계약에 근거 결정 번호를 붙인다. 구현과 다르면 구현을 확인해 고친다 |
| 정본 | `Docs/Narrative/World.md`, `Docs/Narrative/Scenario.md` | 사용자가 승인한 내용만 적고 항목마다 근거 결정을 붙인다. 바꾸려면 사용자 승인과 새 결정이 필요하다 |
| 이력 | `Docs/decisions/`의 결정 파일 본문, 날짜 붙은 QA·검토 보고서, `Docs/Narrative/Research/`의 조사 기록 | 다시 쓰지 않는다. 정정은 새 항목으로 붙인다 |
| 절차 | `Docs/Mentoring.md`, `Docs/AgentContextTools.md`, `Docs/Narrative/Workflow.md` | 실제로 실행한 단계만 적고 단계마다 누가 무엇을 하는지 쓴다 |
| 현황 | `Docs/Work/`의 작업 지도, `Docs/LearningLog.md`, `Docs/Narrative/CurrentWork.md` | 지금 상태와 다음 행동만 적는다. 지난 상태는 이력 문서나 Git이 맡는다 |
| 참조 | `Docs/Decisions.md`, `GLOSSARY.md`, `Docs/NarrativeConcept.md`, `Docs/Narrative/Glossary.md`, 로드맵 | 빠짐없이 적는다. 원본과 다르면 원본이 맞다 |

한 주제는 한 문서가 소유한다. 소유는 [문서 지도](README.md)가 정하고 새 문서는 그 지도에 한 줄로 등록한다. 서사 문서의 소유는 [NarrativeConcept](NarrativeConcept.md)가 정한다. 시스템 학습 문서는 [시스템 학습 문서 작성 규칙](SystemExplanationGuide.md)을 함께 따른다.

## 결정을 기록하는 방법

결정 1건은 `Docs/decisions/NNNN-<english-kebab>.md` 파일 하나다. 근거는 [결정 28](decisions/0028-agent-workflow-restructure.md)이다. `Docs/Decisions.md`는 결정 파일의 머리말에서 생성하므로 손으로 고치지 않는다.

1. `node Tools/Agent/decisions.cjs next`로 다음 번호를 확인하고 파일을 만든다. 머리말에는 `number`, `date`, `title`, `topic`, `status`, `summary`, `owners`를 쓰고, 진행 상태가 있으면 `progress`를 쓴다. 본문은 `# 날짜 — 결정 N: 제목` 아래에 배경, 결정, 트레이드오프 세 절로 이유를 적는다. 기존 파일의 머리말 형식을 따른다.
2. 과거 결정의 본문은 고치지 않는다. 앞선 결정을 바꾸면 새 결정의 머리말에 관계(`refines` 구체화, `amends` 보완, `supersedes_part` 일부 대체, `supersedes` 대체, `lifts_hold` 보류 해제)와 대상 번호를 적고, 본문에 "결정 M을 무엇으로 대체한다"와 이유를 쓴다. 앞선 결정은 머리말의 `status`와 `summary`만 현재 상태에 맞게 고친다. `status`는 `유효`, `유효(부분)`, `번복`, `완료`, `미확인` 중 하나다.
3. `node Tools/Agent/decisions.cjs generate --write`로 `Docs/Decisions.md`를 다시 만들고 `node Tools/Agent/decisions.cjs check`가 통과하는지 확인한다. 검사는 머리말, 번호 순서, 관계 대상, 생성 결과의 일치, 저장소의 모든 `결정 N` 링크를 본다.
4. 확정 수치나 인터페이스가 생겼으면 사양서에 옮기고 결정 번호를 붙인다.

## 검토 순서

1. 사실, 결정, 상태, 출처를 원본과 대조한다.
2. 제목과 문단 첫 문장만 읽어도 흐름이 이어지는지 본다.
3. 긴 문장, 생략된 주어, 모호한 지시어, 불필요한 영어를 고친다.
4. 코드 블록, 직접 인용, 식별자가 원문대로인지 대조한다.
5. 소리 내어 읽었을 때 한 번에 이해되지 않는 문장을 나눈다.
6. `ccl8-writing` 스킬의 참조로 AI 문체, 맞춤법, 표기 일관성을 본다. 표기 일관성은 이 문서를 스타일 가이드로 삼고, 이 문서와 어긋나는 제안은 적용하지 않는다.
7. 마지막에 `ccl8-writing`의 납품 점검을 한다. 참조의 em dash 금지와 전달 이력 금지에는 결정 파일 제목, `결정 N`과 커밋 해시 인용의 예외를 둔다.
