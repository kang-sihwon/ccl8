# ccl8 문서 작성 가이드

저장소에서 사람이 읽는 글을 쓰고 고칠 때 따르는 기준이다. 적용 대상은 `README.md`, `CLAUDE.md`, `AGENTS.md`, `Docs/`의 Markdown 문서, 검토 보고서, 커밋 메시지, 스킬 문서다. 며칠 뒤 다른 기기에서 처음 읽어도 뜻을 이해할 수 있게 쓴다.

## 기본 원칙

- 처음 읽는 사람도 앞선 대화 없이 이해할 수 있게 쓴다. 생략된 대상이나 이전 문맥을 가리키는 표현은 구체적인 문서, 결정, 사건으로 바꾼다.
- 한 문장에는 하나의 중심 판단만 담는다. 조건, 근거, 결과가 길게 이어지면 문장을 나누되 인과관계는 끊지 않는다.
- 사실, 분석, 추론, 미확인을 구분한다. 문장을 다듬으면서 가능성을 단정으로 바꾸거나 원문에 없던 이유를 넣지 않는다.
- 결정과 수치에는 문서에 남아 있는 근거를 함께 적는다. 근거가 없으면 추측해서 채우지 않고 미기록 또는 미확인이라고 밝힌다.
- 비유만으로 설명하지 않는다. 비유를 쓰면 실제로 무엇이 바뀌고 어떤 문제가 생기는지를 이어서 쓴다.
- 결론을 먼저 쓴다. 문서, 절, 문단 모두 결과부터 적고 과정은 뒤에 둔다.

## 제목과 문단

- 제목은 내용을 찾기 쉬운 짧은 명사구로 쓴다. 억지로 완결문으로 늘이지 않는다.
- 본문은 주어와 서술어가 분명한 완결문으로 쓴다. 명사 나열이나 화살표와 등호만으로 관계를 대신하지 않는다.
- 한 문단은 하나의 주제를 다룬다. 배경, 판단, 근거, 후속 조치가 다른 주제면 문단을 나눈다.
- 같은 설명을 여러 문서에 복제하지 않는다. 그 내용을 소유한 문서를 연결하고 현재 문서에 필요한 요약만 남긴다.

## 목록과 표

- 절차 목록은 각 단계에서 누가 무엇을 하는지 알 수 있는 문장으로 쓴다.
- 상태, 이름, 수치, 짧은 분류값은 명사구로 적을 수 있다. 표와 목록에 불필요한 서술어를 붙이지 않는다.
- 표의 한 셀에 서로 다른 판단을 몰아넣지 않는다. 길어지면 셀 안에서 문장을 나누거나 표 아래에서 설명한다.
- 코드, 명령, 경로, URL, 해시는 인라인 코드나 코드 블록으로 구분한다.
- 클래스 다이어그램은 Mermaid `classDiagram` 코드 블록으로 쓴다. GitHub가 렌더링한다.

## 용어와 표기

- 코드, API, 클래스명, 파일명, 명령, 상태값, 스키마 키, 문서 ID, 작품 고유명사는 원래 표기를 유지한다.
- 프로젝트에서 정의한 영어 용어는 처음 등장할 때 뜻을 설명하고, 같은 문서 안에서 표기를 일관되게 쓴다.
- ID를 처음 쓸 때는 `세계의 공간 구성을 정하는 항목(AX-05)`처럼 뜻을 함께 쓴다. ID의 뜻은 해당 영역의 용어집이 소유한다.
- 일반 문장에서는 불필요한 영어를 한국어로 바꾼다. `claim`은 주장, `coverage`는 확인 범위, `mechanism`은 작동 방식이나 구조, `cutoff`는 확인 기준일, `batch`는 작업 묶음이나 차수, `downstream`은 후속 항목이다. `gameplay`는 조작과 규칙을 뜻하면 게임플레이, 진행 과정을 뜻하면 게임 진행이다.
- 절차의 상태값이나 필드 이름으로 쓰는 영어(`canon`, `writer`, `reviewer`, `APPROVED` 등)는 그대로 두고, 일반 설명문에서는 한국어로 쓴다.
- **물결표(`~`)를 쓰지 않는다.** GitHub는 단일 `~`도 취소선 문법으로 파싱해 한 문단에 두 번 나오면 그 사이에 줄이 그어진다. VS Code 미리보기에서는 정상으로 보여 놓치기 쉬우므로 판정 기준은 GitHub 렌더링이다. 범위는 `1-3`, `단계 4-13`처럼 하이픈, 근사값은 `약 5MB`, 이름 접미사는 `...Rad`로 쓴다.
- 새 문서에서는 em dash 대신 쉼표, 마침표, 괄호를 쓴다. `Docs/DesignLog.md`의 제목 형식(`날짜 — 결정 N`)은 예외다.

## 보존해야 하는 기록

- 직접 인용문, 실행한 명령, 실제로 쓴 프롬프트, URL, SHA-256, 출처 원문은 표현을 고치지 않는다.
- 과거 결정과 검토 기록은 현재 기준에 맞춰 소급 변경하지 않는다. 문장은 읽기 쉽게 고칠 수 있지만 당시의 날짜, 판정, 불확실성은 유지한다.
- 경로와 환경 정보는 현행 안내와 과거 기록을 구분한다. 현행 경로는 최신값으로 바꾸고, 과거 이동 기록은 날짜와 함께 남긴다.

## 문서의 종류와 소유

문서를 쓰기 전에 종류를 정한다. 종류가 수정 규칙을 정한다.

| 종류 | 예 | 수정 규칙 |
|---|---|---|
| 규범 | `Docs/Guide.md`, 토픽 규칙 문서, 컨벤션 | 코드나 작업이 규칙을 어기면 규칙을 낮추지 않고 위반을 기록한다 |
| 사양 | 향후 작성할 기능별 사양서 | 확정 수치와 인터페이스 계약만 싣고 근거 결정 번호를 적는다. 구현과 다르면 구현을 확인해 고친다 |
| 이력 | `Docs/DesignLog.md`, 검토 보고서, 완료된 인계문 | 다시 쓰지 않는다. 정정은 새 항목으로 붙인다 |
| 절차 | `Docs/Mentoring.md`, `Docs/AgentContextTools.md`, `Docs/Narrative/Workflow.md` | 실제로 실행한 단계만 적고, 단계마다 누가 무엇을 하는지 쓴다 |
| 현황 | `Docs/LearningLog.md`, `Docs/Narrative/CurrentWork.md` | 지금 상태와 다음 행동만 적는다. 지난 상태는 이력 문서나 git이 맡는다 |
| 참조 | `Docs/Decisions.md`, 용어집, 로드맵 | 빠짐없이 적고, 원본과 다르면 원본이 맞고 참조가 틀린 것이다 |

한 주제의 규칙은 한 문서만 소유한다. 소유 문서는 `Docs/Guide.md`의 문서 지도가 정하고, 새 문서는 그 표에 등록한다. 서사 문서의 소유는 `Docs/NarrativeConcept.md`가 정한다.

시스템의 구현 이유를 교사식으로 설명하고 Git의 이전·현재 코드를 비교하는 학습 문서는 [시스템 학습 문서 작성 규칙](SystemExplanationGuide.md)을 따른다. 비교 학습에 필요한 변경 이력과 커밋은 해당 규칙의 범위에서 본문에 포함한다.

## 결정을 기록하는 방법

1. `Docs/DesignLog.md` 끝에 `## 날짜 — 결정 N: 제목` 절을 붙인다. 번호는 마지막 번호 다음이다. 배경, 결정, 트레이드오프 세 절을 쓰고 이유를 반드시 적는다.
2. 과거 항목은 고치지 않는다. 번복은 새 항목에 "결정 M을 무엇으로 대체한다"와 이유를 적는다.
3. `Docs/Decisions.md`의 해당 주제 표에서 유효 여부, 번복 연쇄, 소유 문서를 갱신한다.
4. 확정 수치나 인터페이스가 생겼으면 사양서에 옮기고 결정 번호를 붙인다.

## 검토 순서

1. 문서의 사실, 결정, 상태, 출처를 확인한다.
2. 제목과 문단 순서만 읽어도 흐름을 따라갈 수 있는지 본다.
3. 긴 문장, 생략된 주어, 모호한 지시어, 불필요한 영어를 고친다.
4. 코드 블록, 직접 인용, 식별자가 원문대로 남았는지 대조한다.
5. 소리 내어 읽었을 때 한 번에 뜻을 이해하기 어려운 문장을 다시 나눈다.
6. `humanizer`, `grammar-checker`, `style-guide` 스킬로 AI 문체, 맞춤법, 표기 일관성을 확인한다. `style-guide`에는 이 문서를 스타일 가이드로 넘긴다. 이 문서와 어긋나는 제안은 적용하지 않는다.
7. `reviewing-technical-prose`의 납품 점검표를 마지막에 적용한다. 그 스킬의 em dash 금지와 전달 이력 금지는 위의 예외(DesignLog 제목, `결정 N`과 커밋 해시 인용)를 따른다.
