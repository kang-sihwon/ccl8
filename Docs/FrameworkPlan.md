# 공용 Framework 분리 계획

공용 게임 시스템을 여러 개인 UE5 프로젝트에서 선택해 사용하는 방향을 계획으로 보관한다. 현재는 문서화만 완료하며 실제 모듈·플러그인 분리와 이름 변경은 보류한다. 작업량과 시스템 연결이 늘어 분리 필요가 구체화되면 사용자가 착수 시점을 정한다. 근거는 [결정 20](DesignLog.md#2026-10-09--결정-20-공용-framework-계획과-구현-보류)이다.

## 목표와 현재 상태

CCL은 공용 시스템을 사용하는 첫 프로젝트로 둔다. 공용 시스템은 상태 소유권, 수명, 실행, 저장·복제 계약을 제공한다. 각 게임은 필요한 시스템을 선택하고 게임 규칙과 콘텐츠를 연결한다.

| 항목 | 상태 |
|---|---|
| 공용화 범위 | 시스템 단위의 재사용 기반 |
| 이름 규칙 | `{Prefix}{System}Framework`를 계획 기준으로 사용 |
| 공통 접두사 | 미정. CCL과 분리된 공용 기반 이름을 추후 선택 |
| 독립 후보 | 아래 목록으로 검토 범위 기록. 추출·독립 실행 검증 전 |
| 실제 분리 | 보류 |
| 착수 시점 | 작업량과 의존 관계를 다시 검토한 뒤 사용자 지정 |
| 환경 후속 작업 | [EnvironmentPlan](EnvironmentPlan.md)의 별도 범위. 이 계획으로 착수하지 않음 |

장르 독립적인 계약과 콘텐츠 분리는 [Coding](Coding.md#장르에-독립적인-베이스-시스템-설계)을 따른다. UE의 기능 선택 기준도 유지한다. 이 계획은 엔진 소스를 수정하거나 UE의 UObject·GAS·Subsystem 등을 자체 구현으로 교체하는 계획이 아니다.

보스, 맵, 퀘스트 내용, 아이템 정의, 화면 구성과 연출 자료는 각 게임이 소유한다. 이 콘텐츠들을 독립 플러그인으로 분리하는 작업은 공용화 범위에 포함하지 않는다.

## 독립 선택의 기준

독립 시스템은 UE5와 작은 공통 계약에는 의존할 수 있지만, 사용하지 않는 다른 게임 시스템을 필수로 요구하지 않아야 한다. 예를 들어 UI만 선택한 프로젝트에는 인벤토리·Agent·지형 구현이 필요하지 않아야 한다.

1. 게임이 공용 시스템을 참조하고, 공용 시스템은 특정 게임의 클래스·맵·에셋을 참조하지 않는다.
2. 게임마다 달라질 규칙과 데이터는 공개 계약으로 전달한다. 변경되지 않는 공통 실행은 시스템이 구현한다.
3. 상태의 소유자, 생성·해제 시점, 서버 권위와 복제 범위를 시스템별로 명시한다.
4. 시스템 사이의 연결은 선택 가능한 어댑터로 둔다. 참조 방향을 바꾸기 위해 모든 데이터를 공통 모듈에 몰아넣지 않는다.
5. 특정 공용 시계나 저장 구현을 강제할지는 실제 계약을 검토해 정한다. 외부 시각·저장 참여 계약만으로 충분한 시스템은 그 입력만 받는다.

현재 CCL의 구현이 이 조건을 모두 만족한다는 판정은 아니다. 시스템을 추출할 때 실제 코드·에셋·설정 의존을 다시 확인한다.

## 이름 규칙

계획의 시스템 접미사는 `Framework`로 통일한다. 최종 이름은 `{Prefix}{System}Framework` 형식으로 정한다. `Prefix`는 자리표시자이며 실제 이름에 그대로 쓰지 않는다. 공통 접두사를 선택한 뒤 엔진·기존 플러그인 이름과 충돌하는지 검사한다.

아래 표는 접두사를 제외한 이름 부분을 보여 준다. 기존 `CCL` 모듈, 클래스와 파일을 지금 이 이름으로 바꾸지 않는다. 내부 구현의 핵심 부분을 설명하는 일반 용어와 시스템의 공식 이름은 구분한다.

표는 분리 목표와 향후 검증 사례다. 개별 시스템의 현재 구현·검증 상태는 관련 사양서가 소유한다. 후보마다 플러그인 하나를 바로 만들거나 후보 전부를 한 번에 추출한다는 뜻은 아니다.

## 선택 확장과 후속 후보

| 기능 | 첫 분리에서의 위치 |
|---|---|
| 장비·소비·탄약 | 아이템 상태와 실행 시스템을 연결하는 선택 확장 |
| 무기·투사체·방어 행동 | 전투 판정과 게임 규칙을 연결하는 선택 확장 |
| Agent 경제·생활·생태 | Agent와 자원·시간·환경을 연결하는 선택 확장 |
| 눈 위 이동·접촉 | 환경 상태와 CharacterMovement를 연결하는 선택 확장 |
| HUD·지도·인벤토리 화면 | 해당 시스템과 공용 UI를 연결하는 게임별 구성 |

물·눈·날씨·열은 `EnvironmentFramework`의 후속 후보로 남긴다. 상호작용과 물질 보존 계약이 강하게 연결되므로 현재는 각각의 독립 플러그인으로 확정하지 않는다. 단계별 구현과 저장·복원 검증을 진행한 뒤 내부 경계를 판단한다.

## 모듈과 플러그인의 경계

모듈은 코드 의존과 공개 API의 경계로 사용한다. 플러그인은 프로젝트에 배치하고 선택하는 시스템 묶음으로 검토한다. 하나의 플러그인에 여러 모듈을 둘 수 있으므로, 시스템 후보와 모듈·플러그인의 수를 미리 일치시키지 않는다. [Epic 모듈 문서](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-engine-modules), [Epic 플러그인 문서](https://dev.epicgames.com/documentation/en-us/unreal-engine/plugins-in-unreal-engine)

특정 시스템만 사용할 때 나머지 시스템을 필수로 불러오지 않는 구성을 우선한다. 공통 계약용 모듈은 실제 공유 자료형과 의존을 확인한 뒤 필요할 때만 추가한다. 런타임 기능과 에디터 도구도 사용 대상과 의존에 맞춰 나눈다.

Game Features 채택, 별도 공용 저장소 생성, 다른 개인 프로젝트 수정은 아직 정하지 않았다. 공용 소스의 저장소와 배포 방법은 추출한 시스템을 별도 프로젝트에서 검증할 때 비교한다.

## 재검토 시점

작업량 증가 자체보다 실제 변경 비용과 재사용 수요를 확인한다. 다음 상황은 분리를 다시 검토할 계기이며 자동 착수 조건은 아니다.

- 한 시스템을 바꿀 때 관련 없는 시스템의 코드·설정까지 반복해서 수정해야 한다.
- 공용 책임과 게임 규칙이 섞여 같은 기능을 다른 맥락에 적용하기 어렵다.
- 두 번째 개인 프로젝트에서 같은 시스템이 필요해 복사·수정이 시작될 상황이다.
- 한 시스템의 공개 계약과 검증 사례가 안정되어 별도로 유지할 근거가 생긴다.
- 시스템별 빌드·테스트·배포를 분리해야 할 구체적인 비용이 확인된다.

파일 수, 코드 줄 수, 환경 단계 번호를 착수 기준으로 고정하지 않는다. 특히 환경 4단계 전에 물리적 모듈 분리를 반드시 완료해야 한다는 일정은 두지 않는다. 다만 여러 시스템의 후보 계산·확정·저장 일관성은 기존 모듈 안에서도 유지해야 한다.

사용자가 공용화 작업을 다시 요청하면 AI는 당시 변경 상태와 의존을 확인하고 첫 추출 대상을 좁힌다. 한 시스템을 추출한 결과를 검토한 뒤 다음 대상으로 넓힌다.

## 착수 후 진행 순서

다음은 실행 전 계획이며 수행 완료 기록이 아니다.

1. AI는 선택한 시스템의 코드·에셋·설정 의존을 조사한다. 기존 결함과 검증 한계를 분리 작업의 기준으로 기록한다.
2. AI는 시스템의 공개 계약, 상태 소유자, 생성·해제, 권위와 저장·복제 경계를 정리한다. 게임별 규칙을 연결할 지점을 정한다.
3. AI는 기존 `CCL` 안에서 구체 게임 타입을 향한 의존을 정리한다. 기존 동작을 먼저 검증한다.
4. AI는 필요한 소스만 모듈·플러그인으로 옮긴다. `Build.cs`, export, 모듈 등록과 타입 경로의 호환을 확인한다.
5. AI는 CCL에서 기존 동작을 확인하고, 별도 최소 프로젝트에서 필요한 시스템만 사용해 독립성을 검증한다.
6. AI는 검증된 공용 코드의 버전과 지원 엔진 범위를 기록한다. 각 게임의 갱신·회귀 검증 방식을 정한 뒤 배포 구성을 선택한다.

착수 때의 우선순위는 재사용 수요와 의존 정리 비용으로 정한다. 현재 목록의 순서가 구현 순서는 아니다. 구체 클래스·함수 시그니처와 파일 이동 목록도 그때 확정한다.

## 분리 완료 기준

| 검증 | 기대 결과 |
|---|---|
| 최소 프로젝트 | 원본 CCL의 헤더·맵·설정 없이 선택한 시스템과 선언한 의존만으로 사용 |
| 게임 규칙 교체 | 공개 데이터·정책·어댑터로 다른 사용 사례를 연결 |
| 선택 사용 | 사용하지 않는 시스템을 끄거나 제외해도 선택한 시스템이 동작 |
| CCL 회귀 | 기존 게임 흐름과 해당 시스템의 자동·수동 검증 유지 |
| 수명·권위 | 맵 이동, 소유자 종료, 클라이언트·서버 분리 시 상태·자원 정리 |
| 저장 호환 | 대상 시스템의 기존 저장 복원 또는 명시적인 버전 변환 |
| 에셋 호환 | 기존 맵·Blueprint의 타입 참조를 실제 로드로 확인 |
| 빌드·패키지 | 필요한 Editor·게임·서버 대상 확인. 불필요한 에디터 의존 제외 |

성능 개선은 분리의 자동 효과로 주장하지 않는다. 빌드 시간, CPU 시간, 메모리와 전송량을 개선 대상으로 삼으면 동일한 조건에서 전후를 측정한다.

## 미정 사항과 비용

공통 접두사, 최초 추출 대상, 정확한 의존 그래프, 플러그인 구성, 공용 저장소, 배포 방법과 착수 날짜는 미정이다. 이 문서는 새 인터페이스나 다른 프로젝트의 지원을 완료했다고 선언하지 않는다.

공용화는 다음 게임에서 구현·검증을 다시 하는 비용을 줄일 수 있다. 대신 공개 API, 저장·에셋 호환, 버전 관리와 별도 프로젝트 검증 비용이 추가된다. 현재는 기능을 실제로 사용하며 경계를 확인하고, 분리 비용을 감당할 근거가 생기면 필요한 시스템부터 진행한다.
