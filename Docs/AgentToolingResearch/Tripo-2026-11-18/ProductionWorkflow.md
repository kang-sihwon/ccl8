# ccl8의 콘셉트 이미지 → Tripo → UE 적용안

콘셉트 이미지로부터 3D 초안을 만드는 경로는 문서상 가능하다. 첫 시험은 같은 입력으로 H3.1과 P2를 비교하고, 채택한 형상에만 후처리를 붙이는 방안을 제안한다. 이 문서는 제작 제안이며 캐릭터 화풍이나 에셋 예산을 확정하는 결정은 아니다. [이미지 생성 API](https://developers.tripo3d.ai/ko/docs/generation-image-to-model/standard), [P 이미지 생성](https://developers.tripo3d.ai/ko/docs/generation-image-to-model/p), [조사 지도](../Tripo-2026-11-18.md)

## 화풍 탐색과 모델 입력 분리

화풍 비교는 실루엣, 비례, 면의 처리, 재질 묘사, 색·명암의 단순화 정도가 달라야 한다. 같은 그림체에서 복장과 색만 바꾸면 디자인 후보는 늘지만 표현 방식의 비교는 되지 않는다. 주인공·NPC·몬스터 각각에서 이 축을 비교하는 방안을 제안한다.

3D 생성에 넘길 때는 선택한 표현을 하나로 고정한다. 아트 감상용 배경·역동적인 포즈·극적인 조명을 그대로 넘기면 대상의 구조와 그림에 포함된 연출을 분리하기 어렵다. 모델링용 이미지는 별도로 정리한다.

| 입력 기준 제안 | 확인할 내용 | 이유 |
|---|---|---|
| 대상 한 개 | 화면 전체의 주인공이 분명하고 잘리지 않음 | 배경·소품을 본체로 해석할 여지 감소 |
| 전신·분리된 팔다리 | 손발과 몸통의 경계가 보임 | 붙은 부위와 숨은 관절을 확인하기 쉬움 |
| 일정한 조명 | 재질색과 강한 명암을 구분할 수 있음 | delight 처리 전후 비교 가능 |
| 시점 일관성 | 정면·측면·후면의 비율과 장식이 일치 | 멀티뷰 입력끼리의 모순 감소 |
| 구조가 보이는 털·장식 | 큰 털 덩어리, 뿔 뿌리, 갑옷 겹침이 읽힘 | 표면 무늬와 실제 형상을 구분 |
| 고정된 디자인 | 얼굴·의상·부위 개수 확정 | 3D 단계의 우발적인 변형을 판정 가능 |

외부 이미지 도구의 사용 여부는 이 기준을 충족하는지로 판단한다. Tripo 자체도 t_pose, character_completion, asset_extraction, 3d_enhance 같은 이미지 템플릿과 멀티뷰 생성 기능을 제공한다. 결과가 원안을 유지하는지는 확인해야 한다. [이미지 편집](https://developers.tripo3d.ai/ko/docs/generation-image-to-image)

## H와 P의 비교 시험

Codex에서 선택한 이미지 한 장을 첨부하고 다음처럼 지시할 수 있다. 첫 문장은 형상 시험, 두 번째 문장은 시안을 채택한 뒤의 별도 작업 예시다. [Codex 사용법](https://developers.tripo3d.ai/ko/docs/codex-plugin)

> @Tripo 3D 첨부한 동물 보스 전신 이미지를 H3.1로 모델링해 줘. 이번에는 형상만 만들고 텍스처와 PBR은 꺼 줘. 뿔과 발을 검토할 수 있게 모델 파일과 가능한 미리보기, 작업 ID를 저장해 줘.

> 방금 고른 모델의 작업 ID를 사용해서 원화 기준으로 텍스처와 PBR을 만들어 줘. 사족 리깅 가능 여부도 검사하고 결과를 보여 줘.

| 후보 | 제안 설정 | 비교할 것 |
|---|---|---|
| H3.1 형상 | model=v3.1-20260211, texture=false, pbr=false | 실루엣·얼굴·뿔·갑옷 구조의 해석 |
| P2 형상 | model=P2-20260801, texture=false, pbr=false, face_limit 명시 | 같은 실루엣의 유지와 토폴로지 |
| 선택 후보의 재질 | v3.5 텍스처, delight와 PBR 명시 | 원화 색상, 구워진 조명, UV 이음새 |
| 선택 후보의 리그 | rig-check 후 체형별 버전 | 실제 굽힘·접지·관통 |

면 수는 시험 대상에 맞춰 정하며 문서 예제의 5,000면을 ccl8의 확정 예산으로 가져오지 않는다. P2 쿼드 후보는 FBX로 나와 미리보기와 후처리 입력 형식도 달라진다. H의 디테일이 더 좋거나 P의 변형이 더 좋다는 결론은 결과를 보기 전까지 미확인이다.

대안은 H 한 종류로 형상을 확정한 다음 리토폴로지를 하는 방식이다. 생성 후보 수는 줄지만 리토폴로지로 실루엣과 관절이 손상될 수 있다. P 직접 생성은 단계가 짧지만 원하는 미세 형상과 표면을 잃을 수 있어 같은 대상 비교가 필요하다.

## 주인공·NPC·동물 보스

| 대상 | 모델 입력에서 강조 | 후처리·검증 제안 |
|---|---|---|
| 주인공 | 얼굴 식별성, 의상 레이어, 손, 장비 부착부 | 얼굴·손 변형, 장비 소켓, 게임 카메라에서 실루엣 |
| 일반 NPC | 종족·직업 차이를 만드는 비례와 의상 | 공유 리그 가능성, 재질·장비 변형의 비용 |
| 일반 몬스터 | 공격 부위와 보행 구조 | 접지·입·꼬리, 실제 충돌과 공격 도달 범위 |
| 동물 보스 | 동물 골격의 설득력, 무게, 과장된 뿔·근육 | 사족 리그, 목·어깨 가동, 털 실루엣, 보스 공격 전용 동작 |

사실적인 털 보스의 원화에서 보이는 가는 털, 열린 입·치아, 얇은 뿔과 장식은 각각 별도 검토 대상이다. 3D 생성 결과에 털이 보인다고 Groom 데이터, 헤어 카드, 물리 반응이 만들어졌다고 판단하지 않는다. 공식 개발자 문서에서 이 결과물 보장을 찾지 못했다.

비휴머노이드 자동 리깅과 걷기 프리셋은 보행 확인용 후보로 사용한다. 몸을 비틀거나 돌진·도약하는 보스 동작, 뿔과 입의 독립 제어, 공격 판정 타이밍은 게임 제작 단계에서 추가로 해결할 범위다. [리깅·프리셋 제약](Animation.md)

## 권장 작업 기록

생성마다 입력 이미지 원본, 요청 JSON 또는 CLI 계획, 실제 모델 버전, seed, task_id, 상위 task_id, credits_consumed를 함께 보존하는 방안을 제안한다. 미리보기와 3D 파일을 모두 저장하고 최종 채택 이유를 남긴다. 임시 다운로드 URL만 남기면 파일 회수가 불안정하다.

| 보존 항목 | 목적 |
|---|---|
| 원본 콘셉트·모델링용 뷰 | 원안과 입력 변환의 차이 추적 |
| model/texture_version/delight/seed | 기본값 변화와 생성 조건 추적 |
| 입력·출력 task_id 관계 | 형상·재질·리그 단계 재개 |
| 단계별 credits_consumed | 생성 한 번과 전체 체인 비용 구분 |
| 모델 파일·텍스처·프리뷰 | 만료 URL과 독립적으로 보관 |
| UE 검사 결과 | 생성 성공과 게임 채택을 구분 |

파일을 바로 게임 Content에 자동 반입하는 대신 검토용 출력 폴더에서 확인하는 방안을 제안한다. 이 조사에서 새 에셋이나 게임 코드는 만들지 않았다.

## 비용 예시

다음은 공개 단가를 더한 시험 예산이다. 한 번씩 성공하고 표준 옵션을 사용하며 할인·재생성·외부 이미지 비용이 없다고 가정한다. 실제 청구액은 credits_consumed로 확인한다. [요금 근거](Operations.md#크레딧과-요금)

| 시험 구성 | 계산, 크레딧 | 환산 |
|---|---:|---:|
| 같은 이미지의 H 형상과 P2 형상 비교 | 20 + 100 = 120 | $1.20 |
| H 이미지 표준 재질 → v3 삼각 리토폴로지+smart_uv → 기본 변환 | 30 + 35 + 5 = 70 | $0.70 |
| P2 이미지 표준 재질 → rig-check → rig → 애니메이션 하나 → 기본 변환 | 110 + 0 + 25 + 10 + 5 = 150 | $1.50 |
| 멀티뷰 생성 → H 멀티뷰 표준 재질 | 10 + 30 = 40 | $0.40 |
| 위 H 멀티뷰에서 시점 두 개 편집 후 생성 | 10 + 2×5 + 30 = 50 | $0.50 |

두 번째 예시의 smart_uv는 리토폴로지 작업에 포함된 옵션이다. 별도 Smart UV가 필요하면 20크레딧을 추가한다. 변환에서 texture_size나 scale_factor 등을 바꾸면 기본 5 대신 고급 10이 될 수 있다. retarget의 animations 배열 5개는 10크레딧 한 번이 아니라 애니메이션별 비용을 고려한다.

성공했지만 디자인이 마음에 들지 않는 작업은 실패 환불과 다르다. 재생성 횟수와 채택률을 별도로 기록해야 에셋 한 개의 실제 제작비를 계산할 수 있다.

## UE 반입 검증안

아래 항목은 시험 계획이다. 현재 UE 5.8.3에서 이 결과를 실행한 것은 아니다. 공식 UE 플러그인의 호환 표는 5.6.0이므로, CLI로 파일을 생성하는 경로와 UE 플러그인 빌드 호환성을 구분한다. [UE 플러그인 안내](https://developers.tripo3d.ai/ko/docs/plugins)

| 단계 | 확인할 결과 | 실패 예 |
|---|---|---|
| 파일 재열기 | 메시·텍스처·리그를 독립 도구에서 표시 | 파일은 있으나 손상되거나 종속 텍스처 누락 |
| Static/Skeletal Mesh 반입 | 의도한 종류와 구조 | 부품 병합, 스켈레톤 누락 |
| 크기·축·피벗 | 게임 기준 치수와 방향 | 정규화·단위 변환 중복, 발 위치 어긋남 |
| 재질 | Base Color·Normal·Roughness·Metallic의 실제 연결 | 맵 누락, 조명 이중 적용, UV 이음새 |
| 리그·애니메이션 | 스켈레톤 대응, 관절 변형·접지·이동 | 어깨 찌그러짐, 발 미끄러짐, 루트 모션 오류 |
| 충돌·소켓 | 이동·피격·장비 부착 | 보이는 형태와 판정 불일치 |
| 성능 | 면 수·재질 슬롯·텍스처 메모리·LOD | 저폴리여도 재질·텍스처 비용 과다 |
| PIE 관찰 | 게임 카메라와 조명에서 식별성·동작 | 뷰어에서는 괜찮지만 전투 화면에서 읽히지 않음 |

검증을 통과한 자산만 채택한다는 기준을 제안한다. 실제 채택과 스타일 확정은 [ArtDirection](../../ArtDirection.md) 및 관련 결정에 기록하고, 도구 간 이미지 비교는 [ConceptImageToolTest](../../ConceptImageToolTest.md)에서 이어간다.

## Fab 건축 후보의 로컬 파일

벨레스 건축 후보 중 아래 패키지는 2026-11-18에 Epic Launcher의 VaultCache에서 실제 UE 에셋 파일을 확인했다. 수량은 각 캐시의 `data/Content` 아래에 있는 `.uasset` 파일 개수다. 패키지마다 표본 파일의 UE 패키지 헤더도 확인했다. [아트디렉션 후보 비교표](../../ArtDirection/VelesBuildingKits-2026-11-18.md)

| 아트 후보 | 로컬 패키지 폴더 | 캐시의 .uasset | ccl8에서 같은 폴더명 확인 |
|---|---|---:|---|
| K01 Modular Medieval Town with Interior | Modular_MedievalTown_WI | 809 | 확인되지 않음 |
| K02 Modular Fantasy House | ModularFantasyHouse | 201 | 확인되지 않음 |
| K05 Stylized Village Fatpack 후보와 폴더명이 대응 | Stylized_Village | 1,052 | 확인되지 않음. 상품 ID 일치는 미확인 |
| K07 Nordic Fishing Hut | Fishermans_Cabin | 2,407 | Content/Fab에 1,246개, Content/TestResources에 45개 |

이 네 폴더는 별도 리소스 프로젝트의 `<ResourceProject>/Content`에도 있다. 기기별 설치 경로는 자리표시자로 표기했다. K01·K02를 시험할 때는 로컬 원본을 사용할 수 있다. 나머지 건축 상품과 Quixel 개별 상품의 전체 다운로드 여부, 모든 의존성의 무결성, ccl8 에디터에서의 로드는 이 파일 확인만으로 확정할 수 없다.
